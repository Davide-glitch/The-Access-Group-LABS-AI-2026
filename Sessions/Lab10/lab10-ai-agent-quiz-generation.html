Last lab's version

A one-shot prompt isn't an agent

var completion = await _chatClient.CompleteChatAsync(messages, new ChatCompletionOptions { ResponseFormat = ChatResponseFormat.CreateJsonSchemaFormat( "quiz", quizSchema, jsonSchemaIsStrict: true) }); var json = completion.Value.Content[0].Text; var payload = JsonSerializer.Deserialize<GeneratedQuizPayload>(json);

One instruction string, one JSON schema, one call. The model can't look anything up, can't ask a follow-up, can't be told "that's wrong, try again" — it either returns usable JSON on the first try or the request fails.

What's missing

No way to check what quizzes already exist. No way to recover from a malformed first attempt except throwing a 502 back at the caller.

The upgrade

What makes something an agent

A chat completion becomes an agent the moment the model can choose to run your code mid-conversation and see what happened before it finishes answering. That's a tool call: the model doesn't run anything itself — it asks, your app executes, the result goes back in the conversation.

→
Requests a tool callwith arguments
→
Your code runsreal logic, real data
→
Model sees the resultand continues

Everything after "Model requests a tool call" is new today — last lab's generator never left the first box.

The library

Microsoft.Extensions.AI does the loop for you

PieceJob
IChatClient a model-agnostic abstraction over any chat client — wraps the same OpenAI.Chat.ChatClient from last lab
AIFunctionFactory.Create(method) reflects a plain C# method into a tool schema — no hand-written JSON schema
UseFunctionInvocation() middleware that runs the tool_call → execute → feed-result-back loop from the previous slide, automatically

You write the tools and the prompt. The loop in the flow diagram is middleware, not code you write by hand.

The design

Two tools, two different jobs

list_existing_quiz_titles

Reads real data — every existing quiz's title and description, via the same IQuizRepository the controller already depends on. Lets the model avoid writing a quiz that duplicates one that already exists.

create_quiz

Doesn't read anything — its arguments are the finished quiz. Calling it is the model's final answer, not a step along the way.

One tool is a side-effect-free lookup. The other one IS the output.

Why this replaces ResponseFormat

A tool's arguments are structured output, for free

[Description("Submit the finished quiz. Call this " + "exactly once, when you're confident.")] private string CreateQuiz( [Description("2+ options, exactly one isCorrect")] List<GeneratedQuestionPayload> questions) { // validate, then stash the result }

AIFunctionFactory.Create reflects this method's parameter type into a JSON schema, the same guarantee ResponseFormat.CreateJsonSchemaFormat gave last lab — except now it lives on a tool, so it doesn't conflict with also offering list_existing_quiz_titles in the same request.

No manual JSON schema. No manual deserialization. The method signature is the contract.

Still your job

A schema guarantees shape, never correctness

foreach (var q in payload.Questions) { if (q.Options.Count < 2 || q.Options.Count(o => o.IsCorrect) != 1) throw new InvalidOperationException( $"Malformed question (\"{q.Text}\")..."); }

Same check as last lab, just reading tool arguments instead of a deserialized completion. Every input you don't control gets checked before you trust it — a tool call is no exception.

A bonus this time

The function-invocation middleware catches this exception and feeds the message back to the model as the tool's result. A malformed first attempt becomes a chance to self-correct, not an automatic failure.

Build it

Three endpoints. The guide walks through each with code to follow along — this part is the map before you start typing.

At a glance

What you're building today

EndpointAuthJob
POST /quizzes/generate required the agent: source text in → tool-calling loop → validated quiz → saved
GET /quizzes/{id}/play public the no-peeking shape — questions and options, no isCorrect
POST /quizzes/{id}/evaluate public submitted picks in → server grades → result with isCorrect revealed

Generating is a write (it creates rows), so it's [Authorize]d. Playing and evaluating are reads/computes over data the server already owns — public, even though one of them is a POST.

A wiring detail that bites

Register the generator Scoped, not Singleton

// last lab: no per-request dependency, Singleton was fine AddSingleton<IQuizGenerator, OpenAiQuizGenerator>(); // today: depends on IQuizRepository (Scoped) AddScoped<IQuizGenerator, OpenAiQuizGenerator>();

The list_existing_quiz_titles tool needs IQuizRepository, which is Scoped because DbContext isn't thread-safe to share.

Captive dependency

A Singleton can't safely depend on a Scoped service — it would pin the first request's DbContext for the app's entire lifetime. .NET throws at startup if you get this backwards.

Endpoint 1

POST /quizzes/generate — the agent

_chatClient = openAiClient .GetChatClient(modelId) .AsIChatClient() .AsBuilder() .UseFunctionInvocation() .Build(); var chatOptions = new ChatOptions { Tools = [ AIFunctionFactory.Create(ListExistingQuizTitlesAsync), AIFunctionFactory.Create(CreateQuiz), ], };

GenerateAsync sends the system+user messages once, then returns whatever CreateQuiz stashed in _result — or throws if the model never called it after several tool-call rounds.

GenerateQuizDto is already defined for you in Dtos/ — the controller action itself looks almost exactly like Lab 9's, just wrapped in the same 502-on-failure handling.

Endpoint 2

GET /quizzes/{id}/play — the no-peeking view

Options = q.Options.Select(o => new PlayOptionDto { Id = o.Id, Text = o.Text }).ToList()

PlayOptionDto simply doesn't have an IsCorrect property — the guarantee is structural, not behavioral. Nothing is being hidden at render time; the field doesn't exist on the type that goes over HTTP.

[AllowAnonymous]

Same reasoning as List() — reading a quiz to play it is a read, not a write.

Endpoint 3

POST /quizzes/{id}/evaluate — grade server-side

The core rule this whole lab keeps coming back to: where is it safe to say a question's correct answer out loud? Never to a client that hasn't submitted an answer yet — which is exactly why grading happens here, not in the browser that already saw the answer-free play shape.

In the database

Fine — the source of truth.

In the play response

Never. That's what PlayOptionDto enforces.

In the evaluate response

Fine — the student already answered.

Wrap-up

The things people trip over on day one, what you'll be able to do after this, and then straight into the guide.

Watch out

Things people get wrong on day one

  • Registering the generator Singleton — it depends on IQuizRepository now; .NET throws a captive-dependency error at startup.
  • Forgetting to validate inside create_quiz — a strict tool schema guarantees shape, never correctness. Skip the check and a malformed quiz saves silently.
  • The model never calls create_quiz — it can get stuck describing the quiz in plain text instead of calling the tool. Your prompt has to say, explicitly, that the tool call is the answer.
Wrap-up

What you can do now

  • Explain, in one sentence, what turns a chat completion into an agent.
  • Design a tool whose arguments are the final answer, instead of a side-effect lookup.
  • Explain why registering a service Singleton can fail once it depends on something Scoped.
  • Explain why a strict JSON schema on a tool call still doesn't remove the need to validate the result.
  • Trace a generated quiz from pasted text, through two tool calls, to a graded result — naming every endpoint it touches.
