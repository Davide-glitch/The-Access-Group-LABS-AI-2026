Testing Across the Stack

From a single C# method to an AI model that never gives the same answer twice — four layers of testing, grounded in the QuizMaster codebase we've been building all along.

→ next   ← previous   F fullscreen

Agenda

Four layers, working outward

  • Backend unit tests — isolating business logic in the API, no database, no network.
  • Frontend unit tests — components and hooks in React, in isolation from the real API.
  • Integration tests — WebApplicationFactory exercising the real pipeline: routing, auth, EF Core.
  • AI testing — the new, harder problem: testing something that doesn't give the same answer twice.
Before we start

Why so many kinds of tests?

Each layer answers a different question, and each one trades speed for realism. The trick isn't picking one — it's knowing which question you're asking before you write the test.

Unit Fast, cheap, narrow — "does this one function do the right thing?"
Integration Slower, fewer of them — "does the whole pipeline actually work?"
AI evals Slowest, fuzziest — "is the output still good, even though it changes?"
Part 1 of 4

Backend unit testing

Testing the C# behind QuizMaster — controllers, services, and grading logic — with no database and no HTTP involved.

Backend unit tests

One method, one behavior, no dependencies

A unit test calls a single method with known inputs and checks a single outcome. Everything that method talks to — the repository, the database, the AI service — gets replaced with a fake that returns exactly what the test needs.

In QuizMaster, that means testing things like QuizzesController.Evaluate or the validation logic around a generated quiz, without ever touching SQL Server or OpenAI.

Why bother

  • Runs in milliseconds — hundreds of them per second.
  • Fails with a precise, specific reason.
  • No flakiness from a database or network being unavailable.
Example · xUnit + a fake repository

Grading logic, in isolation

// Arrange: a fake repository, no real database [Fact] public void Evaluate_ReturnsIncorrect_WhenSelectedOptionIsWrong() { var quiz = QuizFactory.WithOneQuestion(correctOptionId: 1); var repo = Mock.Of<IQuizRepository>(r => r.GetAsync(quiz.Id) == Task.FromResult(quiz)); var controller = new QuizzesController(repo); // Act var result = await controller.Evaluate(quiz.Id, new SubmitQuizDto { SelectedOptionId = 2 }); // Assert: one behavior, checked one way Assert.False(((QuizResultDto)result.Value).IsCorrect); }
Ground rules

What keeps unit tests worth their upkeep

One reason to fail

If a test checks three unrelated things, a single regression gives you three vague failures instead of one clear one.

Name the behavior

Evaluate_ReturnsIncorrect_WhenSelectedOptionIsWrong reads as a sentence — a failing test tells you what broke before you open it.

Fake the boundary, not the logic

Mock IQuizRepository, never the method you're actually testing — otherwise you're testing the mock.

Part 2 of 4

Frontend unit testing

Same idea, different runtime — testing a React component the way a user experiences it, without a real backend behind it.

Frontend unit tests

Render it, interact with it, assert on it

A React unit test renders a single component — QuizCard, PlayQuiz, QuizBuilder — in a virtual DOM, clicks or types like a user would, and asserts on what's on screen. No browser, no real API.

The tools

Vitest React Testing Library jsdom

RTL deliberately queries by text and role — the same things a user sees — not by internal component state.

Example · Vitest + React Testing Library

A quiz card, rendered and queried

test('shows the quiz title and its question count', () => { render(<QuizCard quiz={{ title: 'Photosynthesis', questions: [q1, q2, q3], }} />); expect(screen.getByText('Photosynthesis')).toBeInTheDocument(); expect(screen.getByText(/3 questions/i)).toBeInTheDocument(); });
The one dependency you can't avoid

Stubbing the API layer

vi.mock('../api/quizzes', () => ({ fetchQuizzes: vi.fn().mockResolvedValue([ { id: 1, title: 'Demo Quiz' }, ]), }));

A component like ExistingQuizzes imports fetchQuizzes from api/quizzes.ts — the test replaces that module entirely, so the component never knows it isn't talking to the real server.

Same instinct as mocking IQuizRepository on the backend: fake the boundary, keep the component's own logic real.

Part 3 of 4

Integration testing with WebApplicationFactory

Zoom back out. Boot the real app in memory and send it a real HTTP request — routing, middleware, auth, and the database all in the loop at once.

What changes at this layer

The whole request pipeline, for real

Routing & middleware

The actual ASP.NET pipeline runs — the same routing, model binding, and filters production traffic hits.

Auth

A request without a token really gets a 401 — not a mocked [Authorize] attribute assumed to work.

Data

EF Core talks to a real (if disposable) database, so a broken migration or query shows up here, not in production.

This is the layer that catches "all the unit tests pass but the app doesn't actually boot."

Bootstrap

A test-only version of Program

public class ApiFactory : WebApplicationFactory<Program> { protected override void ConfigureWebHost(IWebHostBuilder builder) { builder.ConfigureServices(services => { // swap the real database for a disposable one services.RemoveAll<DbContextOptions<QuizzesDbContext>>(); services.AddDbContext<QuizzesDbContext>(o => o.UseInMemoryDatabase("tests")); // swap Entra sign-in for a fake scheme the test controls services.AddAuthentication("Test") .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>("Test", _ => { }); }); } }
The tests themselves

Keep them small: request in, response checked

public class QuizzesEndpointsTests : IClassFixture<ApiFactory> { private readonly HttpClient _client; public QuizzesEndpointsTests(ApiFactory factory) => _client = factory.CreateClient(); [Fact] public async Task Get_Quizzes_ReturnsOk() { var response = await _client.GetAsync("/quizzes"); response.EnsureSuccessStatusCode(); } [Fact] public async Task Post_Quiz_WithoutToken_Returns401() { var response = await _client.PostAsync("/quizzes", JsonContent.Create(new { title = "x" })); Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode); } }
The discipline

Integration tests smoke-test the pipeline — they don't re-test logic

It's tempting to let integration tests grow into full scenarios: create a quiz, edit it, submit answers, check every edge case of grading. Resist that — that's what the unit tests already cover, faster and more precisely.

QuestionUnit testIntegration test
Is the grading logic correct?yesno need
Does an unauthenticated POST get a 401?can't — no pipelineyes
Does the app boot with the real DI container?can'tyes

A handful of simple request-in, status-and-shape-checked-out tests beats one that tries to test everything.

Part 4 of 4

Testing AI

Everything so far assumed a deterministic system: same input, same output, every time. That assumption breaks the moment a model is in the loop.

The core problem

What Assert.Equal can't do anymore

Ask the quiz generator for six questions about photosynthesis twice, and you'll get two different — both reasonable — quizzes. There is no single "correct" output to assert against, and the same test can pass today and fail tomorrow with nothing in your code having changed.

Why the old playbook doesn't transfer

  • Non-deterministic — identical input, different output.
  • No ground truth — quality is often a judgment call.
  • Slow and costly to run at scale, unlike a unit test.
  • The model itself changes over time, outside your control.
The toolkit

Three strategies, from systematic to holistic

Evals

A curated dataset of inputs, scored automatically against a rubric — a regression suite for quality.

LLM-as-judge

A second model grades the first model's output against written criteria, at a scale humans can't match.

Human review

Spot-checking real outputs — especially the ones the other two methods can't confidently score.

Layer two

Evals: a regression suite for quality

Build a fixed set of representative inputs — a paragraph about photosynthesis, a paragraph about the French Revolution — and run every prompt or model change against all of them. Score each result against a rubric: are the options plausible, is exactly one correct, is the question actually answerable from the source text.

What it catches that structural checks can't

  • A prompt change that quietly makes questions too easy.
  • A model upgrade that changes tone or difficulty.
  • Regressions you'd otherwise only notice from user complaints.

Same mindset as a unit test suite — run on every change — just scoring "how good," not "pass or fail."

Rounding out the toolkit

Judges, adversaries, and the humans watching production

LLM-as-judge

Faster and cheaper than a human at scale, but it's a model judging a model — imperfect, and worth spot-checking against human judgment.

Adversarial / red-teaming

Deliberately hostile inputs — prompt injection, requests to leak the answer key — to find failure modes before a real user does.

Production monitoring

Log real traffic, watch for drift over time, and treat a thumbs-down from a user as a signal, not noise.

Putting it together

Four layers, one instinct: fake the boundary, keep the logic real

LayerWhat's realWhat's faked
Backend unitThe method under testRepository, AI service, database
Frontend unitThe component under testThe api/ module, the network
IntegrationRouting, auth, EF Core, the app itselfThe database engine, the identity provider
AI evalsThe model, a fixed datasetNothing — you accept the variance and score it instead

Every layer answers a different question. Use the cheapest layer that can actually answer it.
