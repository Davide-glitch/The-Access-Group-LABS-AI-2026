Motivation

Tool calling isn't enough for large document sets

Lab 2 gave the agent live data — current weather, exchange rates, flight search. That works when the universe of facts is small.

But what if you have:

  • 500 internal policy documents
  • 10,000 support tickets
  • A full product knowledge base

You can't fit them all into the prompt. You can't write a tool for each one. You need retrieval.

Context window is finite

Even a 128k token window holds only ~300 pages. And filling it is slow and expensive.

Needle-in-a-haystack fails

Long prompts make models lose focus on the relevant parts. Retrieval precision beats volume every time.

RAG: find, then answer

Retrieve only the 3–5 most relevant chunks. The model has everything it needs, and nothing it doesn't.

Theory

What is an embedding?

An embedding model takes a piece of text and outputs a fixed-size vector of numbers — a point in a very high-dimensional space.

The key property: similar meanings end up close together. The geometry is the semantics.

"How do I reset my password?" → [0.12, -0.87, 0.34, ... 1536 values] "Steps to change account credentials" → [0.11, -0.85, 0.36, ... 1536 values] ↑ very close in vector space
text-embedding-3-small 1536 dimensions

Each dot is a document chunk. Your query lands near the most relevant ones.

Theory

Cosine similarity — direction is meaning

To find relevant chunks, we measure the angle between two vectors. Small angle = similar meaning.

static float CosineSimilarity(float[] a, float[] b) { float dot = 0, magA = 0, magB = 0; for (int i = 0; i < a.Length; i++) { dot += a[i] * b[i]; magA += a[i] * a[i]; magB += b[i] * b[i]; } return dot / (MathF.Sqrt(magA) * MathF.Sqrt(magB)); }

Returns a score between -1 and +1. In practice, text embeddings score between ~0.0 (unrelated) and ~0.95 (near-identical).

Theory

Chunking — why you can't embed a whole document

Embedding models have a token limit (usually 512–8192 tokens). More importantly, a long document produces a vector that averages over all its topics — making it hard to retrieve precisely.

The solution: split documents into smaller, overlapping chunks before embedding.

chunk size overlap precision vs. recall

Start with chunk size 300–500 tokens, overlap 50–100 tokens. Tune from there.

Fixed-size (what we'll use)

Split every N characters with an M-character overlap window. Simple, predictable, works well for most prose documents.

Sentence / paragraph

Split on natural boundaries. Better semantic coherence, but variable chunk sizes need more handling.

Too small → loses context

A 50-token chunk might have the answer but no surrounding context. The model can't form a complete response.

Too large → loses precision

A 2000-token chunk might match too many queries. Retrieval returns irrelevant noise alongside the real answer.

Theory

Vector databases

A vector database stores (id, vector, metadata) tuples and supports fast approximate nearest-neighbour (ANN) search — finding the top-k most similar vectors to a query without comparing all of them.

The dominant index algorithm is HNSW (Hierarchical Navigable Small World graph). Scales to billions of vectors in milliseconds.

Each entry has three parts

  • ID — uniquely identifies the chunk
  • Vector — the embedding (1536 floats)
  • Metadata — source file, page, chunk index, raw text

Architecture

The full RAG pipeline

INGEST
Documents Markdown files, PDFs, tickets…
→
Chunk Split into ~400-token pieces with overlap
→
Embed text-embedding-3-small via GitHub Models
→
Store Vector + metadata in memory
QUERY
User Query "How many leave days do I get?"
→
Embed Query Same embedding model
→
Search Cosine similarity, top-k results
→
Augment Inject chunks into the prompt
→
LLM → Answer Grounded in retrieved text

The ingest phase runs once (or on document update). The query phase runs on every user question.

The LLM never sees the raw documents — only the retrieved chunks. This keeps latency low and the prompt focused.

Integration

RAG as an agent tool

The retrieval pipeline from Lab 3 is just a function. Wrap it in a [Description] attribute and the agent decides when to ground itself in documents vs. answer from general knowledge.

[Description( "Search the company knowledge base for information " + "about policies, procedures, or products. Use this " + "whenever the user asks about internal company topics.")] public static async Task<string> SearchKnowledgeBase( [Description("The user's question, rephrased as a search query")] string query) { var chunks = await RetrieveTopKAsync(query, k: 5); return string.Join("\n---\n", chunks); }

The agent chooses when to call it

Ask "What's the weather in Paris?" — no retrieval. Ask "How many sick days do I get?" — the agent calls SearchKnowledgeBase automatically.

This is the pattern in production

Real-world RAG agents combine this with other tools: web search, database queries, live APIs. Retrieval is one of many grounding mechanisms.

Hands-on · Exercise 01 — 15 min

Build the ingestion pipeline

Load the company docs, chunk them, embed each chunk, and store in-memory. Then test retrieval with a raw query.

  1. Load all .md files from the Docs/ folder
  2. Split each file into chunks of ~1500 characters with 200-character overlap
  3. Call text-embedding-3-small to embed each chunk
  4. Store each (vector, text, source) in a List<Chunk>
  5. Run a test query: embed it, then print top-3 results with similarity scores
record Chunk(float[] Vector, string Text, string Source); var store = new List<Chunk>(); foreach (var file in Directory.GetFiles("Docs", "*.md")) { var text = await File.ReadAllTextAsync(file); foreach (var chunk in SplitIntoChunks(text, 1500, 200)) { var embedding = await EmbedAsync(chunk); store.Add(new Chunk(embedding, chunk, file)); } }

Hands-on · Exercise 03 bonus — 10 min

Tuning chunk size and overlap

Chunk size and overlap are the biggest levers on retrieval quality. In this exercise, experiment and observe.

  1. Re-ingest the docs with chunk size 300, overlap 50
  2. Run the same test queries — do results improve or degrade?
  3. Try chunk size 2000, overlap 400
  4. For each setting, print the top-3 similarity scores and chunk previews

There's no universally correct answer — it depends on the document structure. Learning to tune this by observation is the real skill.

The pattern you'll see

Small chunks → higher similarity scores but less context. Large chunks → lower scores but the answer is in there. Overlap prevents splitting a sentence across chunks.

Going further

Add a source citation to the retrieved text before injecting it into the prompt. Ask the agent to mention where each fact came from.

Stretch goal

After retrieving top-5, re-rank by asking a small LLM: "Which of these chunks best answers the query?" This is called a reranker and dramatically improves precision.

Pitfalls

What can go wrong

  • Chunks too large or too small. Large chunks dilute similarity; small chunks lose surrounding context. Tune empirically — there's no universal answer.
  • Embedding model mismatch. The query and documents must be embedded with the same model. Switching models mid-project invalidates your whole index.
  • Missing metadata. Store the source file and chunk index with every vector. Without it, you can't tell the model where the answer came from — or debug bad retrievals.
  • Retrieving without checking relevance. If top-k returns a score of 0.2, the chunk is probably irrelevant. Add a similarity threshold (e.g. discard anything below 0.5) to avoid injecting noise.
  • Stale index. Documents change. If you update a policy file but don't re-embed it, the agent will answer from old information with full confidence.
  • Top-k too large. Injecting 20 chunks fills the context window and confuses the model. Start with k=3 to k=5.
