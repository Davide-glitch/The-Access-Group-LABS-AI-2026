Recap

What Lab 3 built — and what it can't do

Lab 3's knowledge base is a plain C# list. It works, but every time you start the program:

  • All 6 documents are re-read from disk
  • Every chunk is re-embedded via the API
  • The list is rebuilt from scratch

That costs time and money on every cold start. And you own all the plumbing — cosine similarity, top-k selection, filtering.

The hidden cost

6 documents is fine. At 600 documents, re-indexing on startup takes minutes and burns thousands of embedding API calls.

What we had in Lab 3

var store = new List<Chunk>(); // manual cosine similarity // manual top-k selection // manual threshold filtering // lost on every restart

What we want

  • Persistent storage — index once, query forever
  • Built-in ANN search — no manual cosine loop
  • Field filtering — built into the query
  • Swappable backend — in-memory in dev, Qdrant in prod
Theory

What a vector database actually does

A vector database stores (key, vector, metadata) tuples and exposes fast approximate nearest-neighbour search — the same thing we implemented by hand in Lab 3, but built on a proper index.

The dominant index is HNSW — a graph structure that narrows down candidates in logarithmic time instead of scanning every vector. You never write this code yourself.

You also get metadata filtering applied during the search, not after — which means the top-k you get back are already category-correct.

Persistence

Vectors survive process restarts. Index once when documents change, not on every startup. Critical once your corpus grows past a few dozen files.

Purpose-built ANN index

HNSW finds the nearest k vectors in milliseconds across millions of entries. Our Lab 3 linear scan would take seconds at that scale.

Pre-filter + search

Pass a filter expression alongside the query vector. The DB applies it during traversal — you only pay for the candidates that match.

Abstraction Layer

Microsoft.Extensions.VectorData

Rather than coding directly against a specific database, we code against a standard interface. The backing store becomes a configuration choice, not an architectural one.

API

Defining your record with attributes

You describe the shape of your data with attributes. The connector uses these to map your C# class to the underlying store — no schema files, no migrations.

class Chunk { [VectorStoreKey] public Guid Id { get; set; } = Guid.NewGuid(); [VectorStoreData] public string Text { get; set; } = ""; [VectorStoreData] public string Source { get; set; } = ""; [VectorStoreData(IsIndexed = true)] public string Category { get; set; } = ""; [VectorStoreVector(Dimensions: 1536, DistanceFunction = DistanceFunction.CosineSimilarity)] public ReadOnlyMemory<float> Vector { get; set; } }

[VectorStoreKey]

The unique identifier for each record. Must be a type the connector supports — Guid works for both InMemory and Qdrant.

[VectorStoreData]

A regular payload field. Add IsIndexed = true on fields you'll filter on — this tells the connector to build an index for efficient pre-filtering.

[VectorStoreVector]

Dimensions is required — it must match your embedding model (1536 for text-embedding-3-small). The connector uses it to validate and configure the index.

API

The collection API — upsert and search

A collection is the equivalent of a table or index — a named set of records, all the same type. You get one via the store and interact with it through a typed API.

// get (or create) the collection var col = store.GetCollection<Guid, Chunk>("company-docs"); await col.CreateCollectionIfNotExistsAsync(); // upsert a chunk (insert or update by key) await col.UpsertAsync(new Chunk { Text = chunk, Source = filename, Category = category, Vector = new ReadOnlyMemory<float>(embedding), }); // search — returns IAsyncEnumerable // top is the 2nd positional arg (not a property of options) var options = new VectorSearchOptions<Chunk> { Filter = r => r.Category == "IT", }; await foreach (var hit in col.SearchAsync(queryVector, 3, options)) Console.WriteLine($"{hit.Record.Source} — {hit.Score:P0}");

UpsertAsync

Insert-or-update by key. Calling it twice with the same Id replaces the record — useful for re-indexing updated documents without clearing the whole collection.

SearchAsync → VectorSearchResult

Each result carries result.Record (your Chunk) and result.Score (similarity score). The filter is evaluated inside the index — not as a post-hoc LINQ where clause.

Filter syntax

A LINQ lambda expression: r => r.Category == "IT". Only fields marked IsIndexed = true can be filtered — the connector enforces this at collection creation time.

The Store

Qdrant — the simplest production vector DB

Qdrant is a purpose-built vector database. One Docker command and it's running — no auth, no schema setup, no config files for local dev.

# start Qdrant (data survives container restarts) docker run -d \ -p 6333:6333 \ -v qdrant_storage:/qdrant/storage \ qdrant/qdrant

Then browse to localhost:6333/dashboard — you can see your collections, browse records, and run test queries from the UI.

REST + gRPC HNSW index free & open source

What the .NET connector needs

dotnet add package \ Microsoft.SemanticKernel.Connectors.Qdrant

Collections in Qdrant

Each call to store.GetCollection<Guid, Chunk>("company-docs") maps to a Qdrant collection named company-docs. Qdrant stores the vector + payload fields side by side in its HNSW graph.

Persistence model

Qdrant writes to disk by default (WAL + snapshots). Stop the container, restart it — your vectors are still there. The -v qdrant_storage flag maps the data directory to a Docker volume so it survives container rebuilds too.

Persistence

Skipping re-indexing on warm starts

The moment you switch to Qdrant, you can check whether the collection already exists before running ingestion. On the first run you index. On every subsequent run you skip straight to the agent.

var exists = await collection.CollectionExistsAsync(); if (!exists) { // first run — chunk, embed, upsert Console.WriteLine("Ingesting documents..."); foreach (var file in Directory.GetFiles(docsPath)) { // ... as before } } else { Console.WriteLine( "Collection already indexed — skipping."); }

InMemoryVectorStore — always re-indexes

CollectionExistsAsync() returns false on every startup because the data lives in RAM. The skip logic has no effect — which is fine for development.

QdrantVectorStore — skips on warm start

After the first run, CollectionExistsAsync() returns true and the program goes straight to the agent — zero embedding API calls, instant startup.

Handling document updates

In production you'd check document modification dates and only re-upsert changed chunks. For the lab, re-index by deleting the collection: await collection.DeleteCollectionAsync().

Exercise 01 · 20 min

Migrate to IVectorStore (InMemory)

Replace the List<Chunk> and manual cosine search with the IVectorStore abstraction backed by InMemoryVectorStore.

  1. Convert the record Chunk to a class. Add [VectorStoreKey], [VectorStoreData], and [VectorStoreVector(Dimensions: 1536)] attributes
  2. Change Vector's type from float[] to ReadOnlyMemory<float>
  3. Create IVectorStore vectorStore = new InMemoryVectorStore() and get a typed collection from it
  4. In ingestion, replace store.Add() with await collection.UpsertAsync()
  5. In SearchAsync, replace the LINQ cosine loop with a VectorSearchOptions + collection.SearchAsync() call
  6. Delete the CosineSimilarity method — the DB handles it now

Expected result

Behaviour is identical to Lab 3. Same answers, same latency. The difference is entirely structural — the storage layer is now abstracted and swappable.

Iterating results

await foreach (var hit in collection.SearchAsync(queryVec, options)) { // hit.Record → your Chunk // hit.Score → similarity (0–1) }

Watch out

SearchAsync returns IAsyncEnumerable — you must await foreach it, not .ToList() it directly. Use ToListAsync() from System.Linq.Async if you need a list.

Exercise 02 · 20 min

Swap to Qdrant

With the abstraction in place, switching to Qdrant is three small changes. The rest of the code is untouched.

  1. Add Microsoft.SemanticKernel.Connectors.Qdrant to the project
  2. Comment out new InMemoryVectorStore() — uncomment new QdrantVectorStore(new QdrantClient("localhost"))
  3. Add the CollectionExistsAsync() guard around your ingestion loop
  4. Run the program. Watch it index. Note how long it takes.
  5. Stop the program. Run it again. It should say "Collection already indexed" and skip straight to the agent.
  6. Ask the same questions as in Exercise 01 — results should be identical

The "wow" moment

Second run: zero embedding API calls, instant startup. The index you built in run 1 is still sitting in Qdrant — no rebuild needed.

If you need to re-index

Delete the collection and let it rebuild on the next run:

await collection.DeleteCollectionAsync();

Qdrant not running?

You'll get a connection refused error on the first API call. Make sure Docker is running and the container is up before starting the program.

Pitfalls

What can go wrong

  • Dimension mismatch. [VectorStoreVector(Dimensions: 1536)] must match the embedding model. Swap models and the existing collection is invalid. Always delete and re-index when changing models.
  • Filtering on un-indexed fields. Only fields with IsIndexed = true can be used in a filter. Qdrant will throw at search time if you try. Add the attribute and re-create the collection.
  • Stale collection after document changes. CollectionExistsAsync() only checks if the collection exists — not if it's up to date. Track document modification times or maintain a version hash if freshness matters.
  • Forgetting CreateCollectionIfNotExistsAsync(). Without this, the first upsert on a new collection will fail. Always call it during startup.
  • IAsyncEnumerable not awaited. SearchAsync returns IAsyncEnumerable. Assigning it to a variable doesn't execute it — you must await foreach to get results.
  • Top is not a VectorSearchOptions property. In VectorData.Abstractions 10.1.0, Top was removed from VectorSearchOptions. Pass the count as the second positional argument: SearchAsync(vector, topK, options).
  • Empty-string category filter returns zero results. The LLM passes "" (not null) when no filter is intended. Guard with !string.IsNullOrEmpty(category), not category != null.
  • GitHub Models daily embedding quota. text-embedding-3-small has a separate daily cap. If ingestion hangs, you've likely hit it. Override GITHUB_EMBED_MODEL=openai/text-embedding-3-large to use a different quota pool.
  • Docker volume not mounted. Omitting -v qdrant_storage:/qdrant/storage means data is lost when the container is removed. Always mount the volume in dev so you don't re-index unexpectedly.
