Build a Quizzes Web API from scratch

Start from absolutely nothing — generate the project yourself with dotnet new, then build every layer one piece at a time: model, repository, DI, DTOs, controller. By the end you'll have a working CRUD API and you'll understand why each piece is there.

01

Create the project with dotnet new

Open a terminal inside the Sessions/Lab5/Code folder. It should contain only a README.md right now — that's intentional.

Generate the project:

# scaffold a Web API project with controllers (not minimal APIs) dotnet new webapi -controllers -n Lab5 -o .

Flags explained:

  • webapi — the template name. There are dozens of templates (console, classlib, blazor, …); dotnet new list shows them all.
  • -controllers — use the controller-based pattern, not minimal APIs. (Without this flag, .NET 9+ defaults to minimal APIs.)
  • -n Lab5 — assembly / root namespace name.
  • -o . — output into the current folder instead of a subfolder.

You'll now have:

Lab5.csproj Program.cs appsettings.json appsettings.Development.json Lab5.http Controllers/WeatherForecastController.cs WeatherForecast.cs Properties/launchSettings.json
WeatherForecast? Every dotnet new webapi template ships with a WeatherForecastController example. It's a teaching stub — we'll delete it in the next step before we forget.

Delete the sample files now:

# Linux / macOS / Git Bash rm Controllers/WeatherForecastController.cs WeatherForecast.cs Lab5.http # PowerShell Remove-Item Controllers/WeatherForecastController.cs, WeatherForecast.cs, Lab5.http
02

Swap the default OpenAPI for Swagger UI

The .NET 10 template ships with Microsoft.AspNetCore.OpenApi — which generates the OpenAPI JSON spec at /openapi/v1.json but doesn't include a browsable UI. For this lab we want the familiar Swagger UI page you can poke at with your mouse. That means swapping packages.

Open Lab5.csproj. Replace the existing <ItemGroup> so it references Swashbuckle.AspNetCore instead of Microsoft.AspNetCore.OpenApi:

<ItemGroup> <PackageReference Include="Swashbuckle.AspNetCore" Version="6.8.1" /> </ItemGroup>

Now open Program.cs. The default looks like this:

var builder = WebApplication.CreateBuilder(args); builder.Services.AddControllers(); builder.Services.AddOpenApi(); // ← spec only, no UI var app = builder.Build(); if (app.Environment.IsDevelopment()) { app.MapOpenApi(); // ← spec only, no UI } app.UseHttpsRedirection(); app.UseAuthorization(); app.MapControllers(); app.Run();

Replace it with this:

var builder = WebApplication.CreateBuilder(args); // 1. Register services into the DI container builder.Services.AddControllers(); builder.Services.AddEndpointsApiExplorer(); builder.Services.AddSwaggerGen(); // TODO — register your IQuizRepository here once you've built it. var app = builder.Build(); // 2. Configure the HTTP request pipeline if (app.Environment.IsDevelopment()) { app.UseSwagger(); app.UseSwaggerUI(); } app.MapControllers(); app.Run();
What changed and why
  • AddOpenApi / MapOpenApi → AddSwaggerGen / UseSwagger / UseSwaggerUI. Same idea (read your controllers, produce an OpenAPI spec) but Swashbuckle adds the interactive HTML page at /swagger.
  • AddEndpointsApiExplorer — Swashbuckle needs this service to discover controller actions.
  • Removed UseHttpsRedirection — convenient for local dev but adds a layer of confusion (every http:// call becomes a 307 redirect). Real apps put HTTPS at the load balancer.
  • Removed UseAuthorization — we have no auth in this lab; this middleware is dead weight here.

Last tweak: open Properties/launchSettings.json. Tell it to open Swagger UI in your browser on launch. Replace the file with this minimal version:

{ "$schema": "https://json.schemastore.org/launchsettings.json", "profiles": { "http": { "commandName": "Project", "dotnetRunMessages": true, "launchBrowser": true, "launchUrl": "swagger", "applicationUrl": "http://localhost:5023", "environmentVariables": { "ASPNETCORE_ENVIRONMENT": "Development" } } } }
Optional but recommended in real projects For new APIs in .NET 9+, Microsoft now recommends the built-in Microsoft.AspNetCore.OpenApi + a UI of your choice (Scalar, Redoc, Swagger UI). We're using Swashbuckle here because it's the most-Googled, best-documented option, and matches what you'll see in older codebases. The concepts transfer 1:1.
03

Run the empty shell

From the Code folder:

# builds and runs; auto-reloads when you save a .cs file dotnet watch run

The launch settings open your browser at http://localhost:5023/swagger. You'll see Swagger UI with zero endpoints — just a title bar. That's expected: there are no controllers yet (we deleted the sample one).

Sanity check Terminal shows "Now listening on http://localhost:5023". Swagger page loads but is empty. If you can't reach Swagger, the app isn't running — stop and check the previous two steps before continuing.
The two phases of Program.cs Before builder.Build() you register services into the DI container (AddControllers, AddSwaggerGen). After Build(), you wire up the middleware pipeline (UseSwagger, MapControllers). Mixing the two phases is the #1 day-one mistake — you can't AddX after Build, and you can't UseX before it.

Leave dotnet watch running in this terminal. Every time you save a file, it rebuilds and restarts in a few seconds. Open a second terminal (or your editor) for the rest of the work.

04

Create the domain model

Create a new folder Models, and inside it a file Quiz.cs:

Models/Quiz.cs
namespace Lab5.Models; public class Quiz { public Guid Id { get; set; } = Guid.NewGuid(); public string Title { get; set; } = ""; public string? Description { get; set; } public DateTime CreatedAt { get; set; } = DateTime.UtcNow; }
Why Guid and not int? Integer IDs are great inside a single database, but they leak information ("how many quizzes do you have?") and they collide if you ever shard or merge stores. GUIDs are random, never collide, and can be generated client-side or server-side. For an API ID, default to GUID unless you have a reason not to.
Why = DateTime.UtcNow as a default? We want CreatedAt set automatically when the object is constructed — the client should never supply it. Putting it in the property initialiser keeps that invariant in the model itself, not buried in the repository.

Save the file. dotnet watch will rebuild; Swagger is still empty (no controllers yet) but the project compiles.

05

Define the repository interface

The controller shouldn't know how data is stored. It should ask an abstraction: "give me all quizzes", "find this one", "add a new one". That abstraction is the repository interface.

Create a folder Repositories and inside it:

Repositories/IQuizRepository.cs
using Lab5.Models; namespace Lab5.Repositories; public interface IQuizRepository { IEnumerable<Quiz> All(); Quiz? Find(Guid id); Quiz Add(string title, string? description); bool Update(Guid id, string title, string? description); bool Remove(Guid id); }
Why return bool from Update / Remove? Both can fail for one reason: the ID didn't exist. Returning bool lets the controller turn "not found" into a 404 without throwing an exception. Throwing for control flow is slow and noisy — return a status the caller can act on.
Why does Add take loose parameters instead of a Quiz? Because the repository, not the caller, is responsible for assigning Id and CreatedAt. If we accepted a full Quiz, a careless controller could overwrite those server-owned fields. The signature enforces the boundary.
06

Implement the in-memory repository

Now the concrete class. Same folder:

Repositories/InMemoryQuizRepository.cs
using System.Collections.Concurrent; using Lab5.Models; namespace Lab5.Repositories; public class InMemoryQuizRepository : IQuizRepository { private readonly ConcurrentDictionary<Guid, Quiz> _store = new(); public InMemoryQuizRepository() { Add("C# fundamentals", "Variables, types, control flow, methods."); Add("HTTP basics", "Verbs, status codes, headers."); Add("REST principles", "Resources, idempotency, anti-patterns."); } public IEnumerable<Quiz> All() => _store.Values.OrderBy(q => q.CreatedAt); public Quiz? Find(Guid id) => _store.TryGetValue(id, out var q) ? q : null; public Quiz Add(string title, string? description) { var quiz = new Quiz { Title = title, Description = description }; _store[quiz.Id] = quiz; return quiz; } public bool Update(Guid id, string title, string? description) { if (!_store.TryGetValue(id, out var existing)) return false; existing.Title = title; existing.Description = description; return true; } public bool Remove(Guid id) => _store.TryRemove(id, out _); }
Why ConcurrentDictionary, not Dictionary? Our repo is a singleton (next step) — one instance shared by every request. ASP.NET happily serves requests in parallel, so two threads can call Add simultaneously. A plain Dictionary will corrupt or throw. ConcurrentDictionary handles that for you.
Why seed data in the constructor? Just so GET /quizzes doesn't return an empty array the first time you hit it. Real apps load seed data from migrations, fixtures, or a database — never hard-coded in the repo. For a lab, this is fine.
07

Register the repository in DI

Open Program.cs. Find the comment that says // TODO — register your IQuizRepository here and replace it with a real registration:

using Lab5.Repositories; // at the top of the file // ... builder.Services.AddControllers(); builder.Services.AddEndpointsApiExplorer(); builder.Services.AddSwaggerGen(); builder.Services.AddSingleton<IQuizRepository, InMemoryQuizRepository>();
Why Singleton? Three lifetimes are available:
  • Transient — new instance every time it's asked for. Wrong here: we'd lose our dictionary on every request.
  • Scoped — one per HTTP request. Same problem; we want shared state across requests.
  • Singleton — one instance for the whole app lifetime. Correct for our in-memory store.
Once you swap to a real database, the repo itself becomes scoped (it holds a per-request connection) — the lifetime is part of the design.
What does AddSingleton<IQuizRepository, InMemoryQuizRepository>() actually do? It tells the DI container: "whenever someone asks for an IQuizRepository, give them the same InMemoryQuizRepository instance". The controller will ask for the interface, never the concrete class — that's how you swap implementations later without touching the controller.
08

Create the empty controller

Now we need an endpoint. Create a folder Controllers and inside it:

Controllers/QuizzesController.cs
using Lab5.Models; using Lab5.Repositories; using Microsoft.AspNetCore.Mvc; namespace Lab5.Controllers; [ApiController] [Route("quizzes")] public class QuizzesController : ControllerBase { private readonly IQuizRepository _repo; public QuizzesController(IQuizRepository repo) => _repo = repo; }
What each piece does
  • [ApiController] — opt-in to API conventions: automatic 400 on invalid input, smart parameter binding, problem-details error format.
  • [Route("quizzes")] — base path. Every action method's route is appended to this.
  • : ControllerBase — base class with helpers like Ok(), NotFound(), CreatedAtAction(). (Use Controller instead if you also need views — we don't.)
  • The constructor — DI sees the IQuizRepository parameter, looks it up, and passes in the singleton we registered.

Save. dotnet watch restarts. Refresh Swagger — you'll see "Quizzes" appear as a section, but there are still no endpoints in it. Time to add the first one.

09

GET /quizzes — list everything

Add this method inside QuizzesController:

[HttpGet] public ActionResult<IEnumerable<Quiz>> List() => Ok(_repo.All());
Why ActionResult<T> and not just T? Returning IEnumerable<Quiz> directly works, but you lose the ability to return a different status code (NotFound(), BadRequest()) from the same method. ActionResult<T> lets you do either — return the value (200 OK), or return a status helper. Use it by default.

Try it. Reload Swagger, expand GET /quizzes, click Try it out → Execute.

What you should see 200 OK. Body is a JSON array of three quizzes — the ones seeded in the repo's constructor. Each has an id (GUID), title, description, createdAt.
10

GET /quizzes/{id} — read one

Add a second action method below List:

[HttpGet("{id:guid}", Name = nameof(GetById))] public ActionResult<Quiz> GetById(Guid id) { var quiz = _repo.Find(id); return quiz is null ? NotFound() : Ok(quiz); }
Why the :guid route constraint? Without it, a URL like /quizzes/not-a-guid would reach your method and the model binder would have to deal with the bad input. With {id:guid}, ASP.NET refuses to match the route in the first place — the request gets a 404 before your code runs. Free input validation.
Why Name = nameof(GetById)? We're about to write POST which needs to produce a Location header pointing back here. Naming the route lets us reference it by string-safe identifier instead of hard-coding the URL.

Try it. Run GET /quizzes, copy one of the GUIDs, paste it into GET /quizzes/{id}, execute.

What you should see Real ID → 200 + that quiz. Random GUID (e.g. 00000000-0000-0000-0000-000000000000) → 404. Non-GUID like /quizzes/abc → 404 (route didn't match — you'll see this in the network tab, not Swagger).
11

Input DTOs and validation

Before we write POST, we need to decide what the client is allowed to send. Don't accept a Quiz directly — the client could set Id or CreatedAt and corrupt the model. We use a DTO (data transfer object) — a separate class with only the fields the client may supply.

Create a Dtos folder and add:

Dtos/CreateQuizDto.cs
using System.ComponentModel.DataAnnotations; namespace Lab5.Dtos; public class CreateQuizDto { [Required] [StringLength(200, MinimumLength = 3)] public string Title { get; set; } = ""; [StringLength(2000)] public string? Description { get; set; } }

And a near-identical one for updates:

Dtos/UpdateQuizDto.cs
using System.ComponentModel.DataAnnotations; namespace Lab5.Dtos; public class UpdateQuizDto { [Required] [StringLength(200, MinimumLength = 3)] public string Title { get; set; } = ""; [StringLength(2000)] public string? Description { get; set; } }
Why two near-identical DTOs? They look the same today but they have different meanings. CreateQuizDto describes "what's required to make a new quiz"; UpdateQuizDto describes "what's required to replace an existing one". The day someone adds a field that only matters on create (e.g. InitialAuthorId) or only on update (e.g. VersionToken for optimistic concurrency), you'll be glad they're separate.
The validation magic [Required] + [StringLength] live in System.ComponentModel.DataAnnotations. Because the controller has [ApiController], ASP.NET inspects these attributes before calling your action. If anything fails, it returns 400 Bad Request with a structured error body — you never write the if-statements.
12

POST /quizzes — create

Add a using directive at the top of the controller and the new action:

using Lab5.Dtos; // at the top
[HttpPost] public ActionResult<Quiz> Create(CreateQuizDto dto) { var quiz = _repo.Add(dto.Title, dto.Description); return CreatedAtAction( nameof(GetById), new { id = quiz.Id }, quiz); }
Why CreatedAtAction instead of plain Ok()? Three reasons:
  • It returns status 201 Created, not 200 OK — semantically correct for "I just made a new thing".
  • It builds the URL of the new resource and puts it in the Location header — clients (and the spec) expect this on a 201.
  • It uses nameof(GetById) + a route values object, so if you ever rename the GET action, the compiler will tell you to update this too.

Try it. In Swagger, expand POST /quizzes → Try it out. Send:

{ "title": "REST in practice", "description": "Verbs, status codes, idempotency" }

Then send an invalid body — {"title": ""} or omit title entirely.

What you should see
  • Valid body → 201 Created, response body is the new quiz, response headers include location: /quizzes/<new-guid>.
  • Empty title → 400 Bad Request with a ProblemDetails body listing the failed field.
  • Missing title field → 400, same shape.
  • Title too short (1–2 chars) → 400.
13

PUT /quizzes/{id} — replace

PUT replaces an existing resource. Three outcomes: success, not found, invalid body.

[HttpPut("{id:guid}")] public IActionResult Replace(Guid id, UpdateQuizDto dto) { var updated = _repo.Update(id, dto.Title, dto.Description); return updated ? NoContent() : NotFound(); }
Why IActionResult here, not ActionResult<Quiz>? We never return a quiz body — only a status code (204 or 404). IActionResult is the lighter return type when there's no T to talk about. Use ActionResult<T> only when the happy path returns a body of type T.
Why 204 No Content? The client just sent us the new state of the resource. They already know what they sent. Returning the same data back would be pointless bytes. 204 is the canonical "it worked, nothing more to say" response.
PUT must be idempotent — verify with a quick experiment Send the same PUT body to the same ID twice. The end state should be identical. Our implementation just overwrites fields, so it's fine — but watch for subtleties when you add audit fields. Don't, for example, append to a "change history" list on every PUT; that would make it non-idempotent.
14

DELETE /quizzes/{id}

The simplest endpoint. It either existed (now gone, 204) or it didn't (404).

[HttpDelete("{id:guid}")] public IActionResult Delete(Guid id) => _repo.Remove(id) ? NoContent() : NotFound();
Don't return 200 + a fake body A common mistake on day one is return Ok(new { deleted = true });. That defeats the entire status-code system — a client now has to parse the body to know if the operation succeeded. The HTTP status code is the success signal. Use NoContent().
Idempotent — but only the first call really did something DELETE is idempotent: calling it twice on the same ID is safe. The first call returns 204, the second returns 404. Both are correct. Some APIs return 204 for both — that's defensible too, but 404 on a missing resource is more informative.
15

Test the full CRUD with curl

Swagger is great, but it hides the raw protocol. Walk the API once with curl so you see what's actually going over the wire.

# 1. list — three seeded quizzes curl -s http://localhost:5023/quizzes | jq # 2. create — capture the Location header (-i shows response headers) curl -i -X POST http://localhost:5023/quizzes \ -H "Content-Type: application/json" \ -d '{"title":"HTTP deep dive","description":"All five verbs"}' # 3. read it back — copy the id from the previous response curl -s http://localhost:5023/quizzes/<ID> | jq # 4. replace curl -i -X PUT http://localhost:5023/quizzes/<ID> \ -H "Content-Type: application/json" \ -d '{"title":"HTTP deep dive v2"}' # 5. delete curl -i -X DELETE http://localhost:5023/quizzes/<ID> # 6. confirm it's gone curl -i http://localhost:5023/quizzes/<ID>
Errors to confirm
  • POST with {"title":""} → 400 with a validation message.
  • GET / PUT / DELETE with an unknown GUID → 404.
  • GET / PUT / DELETE with /quizzes/foo → 404 (route constraint blocked it).
  • POST without Content-Type: application/json header → 415 Unsupported Media Type.
If something looks wrong Open browser DevTools (F12) on the Swagger page and watch the Network tab while clicking Execute. You'll see the exact request and response: method, URL, headers, body, status. That's the source of truth, not the rendered Swagger panel.
16

Homework — add Questions to a Quiz

A quiz with no questions is just a title. Extend the API so a quiz can own a collection of questions. Build it using the same five-layer recipe you just learned: model → repo interface → repo implementation → DI registration → controller with DTOs.

Some decisions are deliberately left to you. Make each one explicitly and write a short README.md next to your code explaining what you chose and why.

Design decisions:

  • What does a question look like? (text, an answer, multiple-choice options?)
  • One question type, or several? (true/false, multiple-choice, free-text)
  • How do answers fit? On the question itself, or as a separate concept?
  • Nested URLs (/quizzes/{id}/questions) or a top-level resource with a filter (/questions?quizId=…)? Justify.

Hard requirements:

  • Full CRUD on questions.
  • Each question belongs to exactly one quiz — creating a question against a non-existent quiz returns 404, not 400.
  • Listing a quiz's questions returns them in a deterministic order.
  • Cascade delete. Deleting a quiz removes its questions too.
  • Validation: question text required + length bounds. If you support multiple-choice, at least two options and exactly one correct answer.
  • Correct status codes on every path.
Suggested file layout Mirror what you built today:
  • Models/Question.cs
  • Dtos/CreateQuestionDto.cs, UpdateQuestionDto.cs
  • Repositories/IQuestionRepository.cs, InMemoryQuestionRepository.cs
  • Controllers/QuestionsController.cs
  • Register the new repo in Program.cs.
Cascade-delete — two reasonable approaches
  • From the quiz repo: have InMemoryQuizRepository.Remove also call into the question repo. Simple, but couples the two repos.
  • From the controller: in QuizzesController.Delete, call both repos. Cleaner separation, more code at the call site.
Either is fine — pick one and explain it in your README.
Stretch goal Add POST /quizzes/{id}/attempts: the client submits a set of answers; the server scores them and returns the result. Forces you to design a non-CRUD action endpoint — what shape is the request body, what does the response carry, what's the correct status code?

That's the lab.

You built every layer of a working CRUD API from a blank slate: model, repository, DI, DTOs, controller, five endpoints. Everything else in ASP.NET — auth, EF Core, background services, custom middleware — is more of these same patterns layered on top.
