Part 1 · Web apps

A web app is a program split in two

Every web app is two programs talking over a network:

  • A client that runs on the user's device (a browser, a mobile app, even another server)
  • A server that runs on a machine somewhere else, owned by whoever made the app

They communicate by sending messages back and forth. The client asks for something; the server answers. That's it.

The protocol they use to do this is HTTP — the rules for how those messages are shaped.

The client

The thing the user sees and clicks. A browser rendering HTML. A mobile app. A desktop app. Even a script you wrote yourself.

The server

The thing that holds the data, runs the business logic, and decides what to send back. This is what we're going to build.

The network in between

Slow, unreliable, public. Anything you send over it is visible — which is why HTTPS, auth, and validation matter.

Part 1 · Web apps

What happens when you visit a URL

You type https://example.com/quizzes and press Enter. Roughly six things happen, in this order:

  1. DNS lookup. The browser asks "what IP address is example.com?" and gets back something like 93.184.216.34.
  2. TCP connection. The browser opens a network connection to that IP on port 443 (HTTPS) or 80 (HTTP).
  3. TLS handshake. If HTTPS, the two sides agree on an encryption key so nobody on the network can read what comes next.
  4. HTTP request. The browser sends a text message: "GET /quizzes, here are my headers". This is the part we care about.
  5. HTTP response. The server sends a text message back: a status code, headers, and a body (HTML, JSON, an image, whatever).
  6. Render. If the body is HTML, the browser parses it, makes more requests for CSS / JS / images, and draws pixels.

We're going to spend almost all our time on step 4 and 5 — the HTTP request and response. That's where the API lives.

Part 1 · Web apps

Frontend, backend, and the API in between

Modern apps usually split into two halves that are developed and deployed separately:

  • Frontend — what the user sees. HTML, CSS, JavaScript, running in the browser. Or a mobile app's UI code.
  • Backend — the server logic. Where your data lives, where business rules run, where authentication happens.

The frontend can't talk to the database directly — it sits on someone else's untrusted device. It has to ask the backend for everything.

That "asking" is the API. A well-defined set of HTTP endpoints the frontend (or anyone else) can hit.

Browser / Mobile / Script The client — sends HTTP requests
↓ HTTP
Web API (today's lab) Routes, validates, runs business logic
↓ SQL / driver call
Database Where data actually lives

One backend can serve many frontends — a web app, a mobile app, a partner integration — without changing.

Part 1 · Web apps

"API" demystified

API stands for Application Programming Interface. Don't let the name intimidate you — it's just a contract.

It says: "if you send me a message shaped like this, I'll send you back a message shaped like that."

In our world, that contract is a list of HTTP endpoints. Each one specifies:

  • The URL to hit (/quizzes/{id})
  • The HTTP verb to use (GET, POST, ...)
  • What data to send (if any)
  • What you'll get back (and what could go wrong)

An API is not a technology

It's not a framework, a language, or a library. It's a written promise. ASP.NET, Express, FastAPI, Spring — they're all just tools to build APIs. The API itself is the agreement.

Why this matters

Once the contract is written down, the frontend team and the backend team can work in parallel. Anyone can build a client. The API is the integration point.

Part 2 · HTTP

Anatomy of an HTTP request

An HTTP request is just text sent over a socket. Four pieces:

  • Start line — verb, path, protocol version
  • Headers — key/value metadata about the request
  • Blank line — separates headers from body
  • Body (optional) — payload, usually JSON for APIs

The server reads this, figures out what was asked, and writes a response back in the same format.

POST /quizzes HTTP/1.1 Host: api.example.com Content-Type: application/json Accept: application/json Authorization: Bearer eyJhbGc... Content-Length: 63 ──────────────────────────── { "title": "C# fundamentals", "description": "Variables, types, methods" }
Part 2 · HTTP

Anatomy of an HTTP response

The response mirrors the request:

  • Status line — protocol, numeric code, short text
  • Headers — about the response (type, length, caching)
  • Blank line
  • Body — the actual data the client asked for

The status code is the single most important byte the client reads. It tells you "did this work?" before you parse anything.

HTTP/1.1 201 Created Content-Type: application/json Location: /quizzes/8c4e Content-Length: 128 ──────────────────────────── { "id": "8c4e...", "title": "C# fundamentals", "description": "Variables, types, methods", "createdAt": "2026-05-28T10:14:00Z" }
Part 2 · HTTP

The verbs that matter

HTTP has many verbs. In practice, you'll use five.

Verb Intent Has body? Safe Idempotent
GET Read a resource. Should never change server state. No yes yes
POST Create a new resource (or trigger an action). Yes no no
PUT Replace a resource entirely with the body you send. Yes no yes
PATCH Modify part of a resource. Send only what changed. Yes no depends
DELETE Remove a resource. No no yes

Safe = doesn't change state. Idempotent = doing it twice has the same effect as doing it once.

Part 2 · HTTP

Headers, statelessness, and CORS

Headers worth memorising

  • Content-Type — what's in the body I'm sending (application/json)
  • Accept — what format I'd like back
  • Authorization — who I am (Bearer <token>, Basic ...)
  • Cache-Control — how the response may be cached
  • Location — set by the server on 201 Created to point at the new resource

HTTP is stateless

The server doesn't remember the previous request. Every request must carry everything it needs — the URL, the body, and the auth header that proves who you are. There are no "sessions" at the protocol level; we fake them with tokens or cookies.

CORS — you'll meet this later

Browsers refuse to let JavaScript on site-a.com call api.site-b.com unless the API explicitly allows it via Access-Control-Allow-Origin. Mention-only for now — we won't need it today.

Part 2 · HTTP

Tools you'll use every day

Browser DevTools

Open F12 → Network tab. Every request the page makes is listed: verb, URL, status, headers, body. Your first stop for "why is this broken?"

curl

Command-line HTTP. Scriptable, copy-pasteable, lives everywhere. If you can hit an endpoint with curl, you understand it.

curl -X POST \ http://localhost:5000/quizzes \ -H "Content-Type: application/json" \ -d '{"title":"C#"}'

Swagger UI

An auto-generated web page that lists every endpoint your API exposes, with a form to try each one. Shipped out of the box with ASP.NET — we'll use it heavily today.

Postman and Bruno are popular GUI alternatives to curl. Pick whichever feels good — the concepts are identical.

Part 3 · REST

REST — a convention for organising HTTP

REST is not a framework or a spec. It's a style for designing HTTP APIs that almost everyone uses today.

The core idea: model your system as a set of resources (nouns), and use HTTP verbs to act on them.

  • Quizzes are a resource. So are questions, users, scores.
  • Each resource has a URL. /quizzes is the collection; /quizzes/8c4e is one specific quiz.
  • The verb says what to do. The URL says what to do it to.

Why bother with conventions?

Because anyone landing on your API for the first time should be able to guess what endpoints exist. GET /quizzes lists quizzes. Obviously. POST /quizzes creates one. Obviously.

A surprising API is a slow-to-learn API.

It's HTTP, used well

REST = "do what HTTP was already designed to do." Verbs as verbs. Status codes as status codes. URLs as resource identifiers. That's most of it.

Part 3 · REST

Designing URLs for the Quizzes API

Verb URL What it means Success status
GET /quizzes List all quizzes 200
GET /quizzes/{id} Read one quiz 200
POST /quizzes Create a new quiz 201
PUT /quizzes/{id} Replace an existing quiz 204
DELETE/quizzes/{id} Delete a quiz 204
GET /quizzes/{id}/questionsList questions of a quiz (homework)200
  • Plural nouns for collections. /quizzes, not /quiz.
  • No verbs in URLs. Never /getQuiz or /createQuiz — the HTTP verb already says that.
  • Nested resources express ownership. A question belongs to a quiz, so /quizzes/{id}/questions.
Part 3 · REST

Idempotency & safety — why they matter

The network is unreliable. Requests time out. Mobile clients retry. Proxies replay. You need to know what happens when the same request arrives twice.

Safe — the request doesn't change anything. GET is safe; you can call it a thousand times and nothing changes.

Idempotent — calling it twice has the same effect as calling it once. PUT /quizzes/8c4e with the same body, twice → end state identical.

This is why POST is the verb for "create" — each call produces a new resource. Two POST /quizzes calls = two quizzes.

The retry rule

Clients can safely retry any idempotent or safe verb on a timeout. They cannot safely retry POST — they might create the same thing twice.

Practical consequence

When you design an endpoint, pick the verb that matches the semantics you actually want. "Create" is POST. "Replace" is PUT. "Tweak" is PATCH. Don't use POST for everything.

Versioning — brief note

When the contract changes in a breaking way, version the URL: /v1/quizzes → /v2/quizzes. Header-based versioning exists too; URL is the simplest pragmatic choice.

Part 3 · REST

Common REST anti-patterns

  • Verbs in the URL. POST /createQuiz, GET /listAllQuizzes. The URL should describe the resource, not the action.
  • Always returning 200, even on errors. Sending 200 OK with a body like {"error":"not found"} defeats the entire status-code system — clients can't tell success from failure without parsing the body.
  • GET with side effects. If GET /quizzes/{id}/delete deletes the quiz, every crawler and cache prefetch will wipe out your data. GET must be safe.
  • Returning raw entities with internal fields. Database IDs of related rows, internal flags, audit columns. Send only what the client needs (use a DTO).
  • Inventing custom verbs as URL suffixes. POST /quizzes/{id}/publish is sometimes a pragmatic exception (state transitions), but used carelessly it becomes RPC dressed as REST.
  • Inconsistent naming. /quizzes, then /Question_List, then /userScores. Pick a casing (kebab or lower) and stick to it.
Part 4 · ASP.NET

Where ASP.NET Core sits

ASP.NET Core is Microsoft's framework for building web servers in C#. It's:

  • Cross-platform — runs on Windows, Linux, macOS.
  • Open-source — github.com/dotnet/aspnetcore.
  • Fast — among the top web frameworks in public benchmarks.
  • Batteries included — routing, DI, logging, config, model binding, validation, OpenAPI — all in the box.

It supports several application styles. We're using Web API with controllers, the most common shape for HTTP services.

Two API styles in .NET

Minimal APIs — endpoints registered inline in Program.cs. Great for tiny services.

Controllers — endpoints as methods on classes, organised by resource. Standard for anything non-trivial. We're using this.

Why controllers for learning

One file per resource, clear separation, attribute-driven routing. The pattern scales to large apps and is what you'll see in real codebases.

Part 4 · ASP.NET

Program.cs — builder, services, middleware

var builder = WebApplication.CreateBuilder(args); // 1. Register services into the DI container builder.Services.AddControllers(); builder.Services.AddEndpointsApiExplorer(); builder.Services.AddSwaggerGen(); builder.Services.AddSingleton<IQuizRepository, InMemoryQuizRepository>(); var app = builder.Build(); // 2. Configure the HTTP request pipeline (middleware) if (app.Environment.IsDevelopment()) { app.UseSwagger(); app.UseSwaggerUI(); } app.UseHttpsRedirection(); app.MapControllers(); app.Run();

Phase 1 — register services

Before Build(), you tell the DI container which classes exist and how to construct them. Controllers will be able to ask for any of these in their constructors.

Phase 2 — middleware pipeline

Every request flows through middleware in order: HTTPS redirect, routing, auth, then your controller. Each piece can short-circuit or pass through. Think of it as an onion around your endpoint.

The two-phase rule

You can't AddX() after Build(), and you can't UseX() before it. Forgetting this is a classic first-day-on-the-job mistake.

Part 4 · ASP.NET

Controllers — endpoints as methods

[ApiController] [Route("quizzes")] public class QuizzesController : ControllerBase { private readonly IQuizRepository _repo; public QuizzesController(IQuizRepository repo) => _repo = repo; [HttpGet] public ActionResult<IEnumerable<Quiz>> List() => Ok(_repo.All()); [HttpGet("{id:guid}")] public ActionResult<Quiz> GetById(Guid id) { var quiz = _repo.Find(id); return quiz is null ? NotFound() : Ok(quiz); } }

[ApiController]

Turns on automatic 400 responses for invalid models, infers body/query/route binding, and adds ProblemDetails-style errors.

[Route] and [HttpGet]

[Route("quizzes")] sets the base path. [HttpGet("{id:guid}")] appends a parameter and validates it's a GUID — non-GUIDs get a 404 before your code runs.

Action results

Ok(...), NotFound(), CreatedAtAction(...), NoContent(), BadRequest(...) — helpers that produce the right status code with the right shape.

Part 4 · ASP.NET

DTOs and validation

Never accept your domain model directly from the request. Use a DTO (data transfer object) — a class describing exactly what the client may send.

public class CreateQuizDto { [Required] [StringLength(200, MinimumLength = 3)] public string Title { get; set; } = ""; [StringLength(2000)] public string? Description { get; set; } } [HttpPost] public ActionResult<Quiz> Create(CreateQuizDto dto) { var quiz = _repo.Add(dto.Title, dto.Description); return CreatedAtAction(nameof(GetById), new { id = quiz.Id }, quiz); }

Why a separate DTO?

The client shouldn't be able to set Id, CreatedAt, or any future internal field. The DTO is your input contract; the domain model is your internal shape.

Validation is automatic

With [ApiController], invalid input never reaches your method — ASP.NET returns 400 Bad Request with a structured error body listing each failed rule.

Annotations available

[Required], [StringLength], [Range], [RegularExpression], [EmailAddress], [Url]. From System.ComponentModel.DataAnnotations.

Part 4 · ASP.NET

Dependency injection in 5 minutes

Controllers don't new up their dependencies. They ask for them in the constructor, and the framework supplies an instance.

// Program.cs — register builder.Services.AddSingleton<IQuizRepository, InMemoryQuizRepository>(); // QuizzesController.cs — receive public QuizzesController(IQuizRepository repo) => _repo = repo;

Every time a request arrives, ASP.NET builds a QuizzesController and hands it an IQuizRepository — no factory code, no globals.

Three lifetimes

  • Singleton — one instance for the whole app. Good for our in-memory repo.
  • Scoped — one per HTTP request. Default for database contexts.
  • Transient — a new one every time it's requested.

Why this matters

You can swap the implementation in one place — Program.cs — and every controller picks up the change. Want a SQL-backed repo tomorrow? Register SqlQuizRepository instead. Controllers don't change.

Part 4 · ASP.NET

Swagger / OpenAPI — free documentation

ASP.NET reads your controllers, parameters, return types, and attributes — and produces an OpenAPI document describing your entire API.

Swagger UI renders that document as an interactive web page. Each endpoint can be expanded, parameters filled in, and the request sent — all without leaving the browser.

For learning and debugging, this is gold: you can build your API and try it without writing a single line of client code.

Where to find it

Run the app and open http://localhost:<port>/swagger. The raw spec is at /swagger/v1/swagger.json.

What it captures

  • Every endpoint + its verb + its route
  • Parameter types and locations (route, query, body)
  • Request body schema (from your DTOs)
  • Response types and possible status codes
  • Validation rules from your annotations

It's also a contract

Frontend teams generate typed client code straight from the spec. Keep your DTOs and attributes honest and the contract is always up to date.

Part 5 · Hands-on

Lab — build the Quizzes API

Start from the skeleton in Sessions/Lab5/Code. By the end of the session your API should support full CRUD over Quiz with proper status codes, validation, and Swagger.

  1. Create the project. dotnet new webapi -controllers -o QuizzesApi, then run it and confirm Swagger loads.
  2. Define the domain model. A Quiz class with Id (Guid), Title, Description, CreatedAt.
  3. Add an in-memory repository. IQuizRepository with All, Find, Add, Update, Remove. Back it with a ConcurrentDictionary<Guid, Quiz>. Register as singleton.
  4. Build the controller. QuizzesController with five endpoints: GET /quizzes, GET /quizzes/{id}, POST /quizzes, PUT /quizzes/{id}, DELETE /quizzes/{id}.
  5. Add DTOs and validation. CreateQuizDto, UpdateQuizDto. [Required] on title, length bounds, description optional.
  6. Return correct status codes. 200 on read, 201 + Location on create, 204 on update/delete, 404 when missing, 400 on invalid input.
  7. Test in Swagger and curl. Run through the happy path and three error cases (missing title, unknown id, malformed GUID).
Homework

Extend the API with Questions

A quiz needs questions. Your job is to design and implement the Question resource on top of what you built today.

Some decisions are deliberately left to you — design is part of the exercise.

  • What fields does a question have?
  • One question type, or several (multiple-choice, true/false, free-text)?
  • How do answers fit? Stored on the question, or a separate concept?
  • What URL shape — nested under quiz, or a top-level /questions resource?

Minimum requirements

  • Full CRUD on questions
  • Questions belong to a specific quiz
  • Listing a quiz's questions returns them in order
  • Deleting a quiz cascades — its questions go too
  • Validation: question text required, length bounds, sensible answer rules
  • Correct status codes everywhere (404 if quiz doesn't exist, etc.)

Stretch

Add a POST /quizzes/{id}/attempts endpoint: the client submits answers, the server scores them and returns the result. Forces you to think about request shape, server-side logic, and what to return.

Pitfalls

Things people get wrong on day one

  • Returning 200 for everything. A successful create is 201 Created; a successful delete is 204 No Content. Use Ok, CreatedAtAction, NoContent — not just Ok.
  • Forgetting the Location header on 201. CreatedAtAction(nameof(GetById), new { id = quiz.Id }, quiz) sets it for you — don't hand-roll it.
  • Letting clients set the Id. If your DTO has an Id field, a malicious client can overwrite anything. Server generates the ID; DTO doesn't have one.
  • Exposing the domain model directly. Add a field to Quiz and it leaks into every response. Always project into a DTO on the way out, even if it looks identical today.
  • Using POST for updates. PUT for full replace, PATCH for partial. POST is only for "create new" (or, exceptionally, RPC-style actions you can't model otherwise).
  • No validation, then surprise 500s. Without [Required] and length bounds, a null title sails into your repo and the next read crashes. Validate at the boundary.
  • Singleton repo with mutable shared state, but no concurrency control. A plain Dictionary isn't thread-safe; two simultaneous requests can corrupt it. Use ConcurrentDictionary.
