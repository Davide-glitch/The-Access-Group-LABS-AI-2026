Expose your API as MCP tools

You built a persisted Quizzes API. Now make its operations available to an AI agent as MCP tools — over the Streamable HTTP transport, hosted inside the same app — and drive it from GitHub Copilot in VS Code. In Lab 2 you taught an LLM to call tools; here you publish your own.

What is MCP? The Model Context Protocol is an open standard for how AI agents discover and call external tools. A host (VS Code Copilot, Claude, etc.) connects to an MCP server, asks it which tools exist (tools/list), and invokes them (tools/call). Your server just describes some functions; the agent decides when to use them. We'll expose the quiz operations so an agent can list, read, create quizzes and add questions — writing straight into your SQL Server database.

Prerequisites

Start from your finished Lab 6 — the async, EF Core + SQL Server solution. You'll add the MCP server on top of it.

  • Your Lab 6 API running against SQL Server (LocalDB or Docker).
  • VS Code 1.102+ with the GitHub Copilot and Copilot Chat extensions, and access to agent mode.
  • The .NET 10 SDK (you already have it).
This part needs VS Code, not full Visual Studio MCP servers are configured for Copilot through .vscode/mcp.json. If you don't have Copilot agent mode, you can still complete and test everything with the MCP Inspector fallback in Step 4.
01

Add the MCP package

The official C# SDK has an ASP.NET Core package that plugs an MCP server into your existing web host and serves it over Streamable HTTP.

# from inside your Lab 6 project folder dotnet add package ModelContextProtocol.AspNetCore --prerelease

That pulls in ModelContextProtocol.AspNetCore (v1.3.0 at time of writing) and the core SDK it depends on.

Why the ASP.NET Core package, not the plain SDK? The base ModelContextProtocol package is enough for a stdio server (a console process the host launches). We want Streamable HTTP — the server is a normal HTTP endpoint that any client can connect to over the network. That transport lives in the .AspNetCore package and reuses the web host you already have.
02

Write the tools

A tool is just a method. Mark a class with [McpServerToolType] and each exposed method with [McpServerTool]. The [Description] attributes are not decoration — they're what the agent reads to decide when and how to call your tool.

Create a Mcp folder and add:

Mcp/QuizTools.cs
using System.ComponentModel; using Lab6.Models; using Lab6.Repositories; using ModelContextProtocol.Server; namespace Lab6.Mcp; [McpServerToolType] public class QuizTools { [McpServerTool(Name = "list_quizzes")] [Description("List all quizzes, including their questions.")] public static async Task<IEnumerable<Quiz>> ListQuizzes(IQuizRepository repo) => await repo.AllAsync(); [McpServerTool(Name = "get_quiz")] [Description("Get a single quiz by its id, including its questions.")] public static async Task<Quiz?> GetQuiz( IQuizRepository repo, [Description("The quiz id (GUID).")] Guid id) => await repo.FindAsync(id); [McpServerTool(Name = "create_quiz")] [Description("Create a new quiz. Returns the created quiz with its generated id.")] public static async Task<Quiz> CreateQuiz( IQuizRepository repo, [Description("The quiz title.")] string title, [Description("Optional quiz description.")] string? description = null) => await repo.AddAsync(title, description); [McpServerTool(Name = "add_question")] [Description("Add a question to an existing quiz. Returns the updated quiz, or null if it does not exist.")] public static async Task<Quiz?> AddQuestion( IQuizRepository repo, [Description("The id (GUID) of the quiz.")] Guid quizId, [Description("The question text.")] string text) => await repo.AddQuestionAsync(quizId, text); }
Where does IQuizRepository come from? The SDK resolves tool-method parameters two ways: values the agent supplies (the ones with [Description], like title) come from the tool call; everything else is resolved from dependency injection. Each tool call runs inside its own DI scope, so the scoped repository — and its DbContext — are created and disposed per call, exactly like an HTTP request. Your tools reuse the same storage path as the controller.
No serialization cycle? Returning Quiz works because Question.Quiz is already [JsonIgnore] from the main lab. The SDK serializes the return value to JSON for the agent. (In a real server you'd return response DTOs — same lesson as the API.)
03

Map the Streamable HTTP endpoint

Two additions to Program.cs: register the MCP server (discovering tools from this assembly) and map its endpoint.

With the other service registrations:

builder.Services .AddMcpServer() .WithHttpTransport() // Streamable HTTP, not stdio .WithToolsFromAssembly(); // find [McpServerTool] methods

And after app.MapControllers():

app.MapControllers(); app.MapMcp("/mcp"); // MCP served at http://localhost:5023/mcp app.Run();
What "Streamable HTTP" means It's the current MCP transport (it replaced the older HTTP+SSE one). The client POSTs JSON-RPC messages to your endpoint; the server can reply with a single JSON response or stream multiple messages back as Server-Sent Events over the same connection — useful for progress and notifications. The SDK handles all of that; you just map the route. A session id is exchanged via the Mcp-Session-Id header.
Verify dotnet build is clean. Your app now serves the REST API and the MCP endpoint from the same process on port 5023.
04

Run & smoke-test

dotnet run

The REST API is unchanged at /quizzes. The MCP server is now at /mcp. You can confirm it's alive before involving any agent — an MCP client must initialize first, then it can list tools:

# 1. initialize — note the Mcp-Session-Id response header curl -i -X POST http://localhost:5023/mcp \ -H "Content-Type: application/json" \ -H "Accept: application/json, text/event-stream" \ -d '{"jsonrpc":"2.0","id":1,"method":"initialize", "params":{"protocolVersion":"2024-11-05","capabilities":{}, "clientInfo":{"name":"curl","version":"1.0"}}}' # 2. list tools — reuse the session id from the header above curl -X POST http://localhost:5023/mcp \ -H "Content-Type: application/json" \ -H "Accept: application/json, text/event-stream" \ -H "Mcp-Session-Id: <paste-from-step-1>" \ -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'

You should see your four tools with their descriptions and input schemas.

No-Copilot fallback: MCP Inspector The official visual tester. With your app running:
npx @modelcontextprotocol/inspector
In the browser it opens, choose transport Streamable HTTP, URL http://localhost:5023/mcp, connect, and click your tools to run them. No Copilot licence needed.
05

Connect VS Code + GitHub Copilot

Tell VS Code where your MCP server lives. Create a workspace config file:

.vscode/mcp.json
{ "servers": { "quizzes": { "type": "http", "url": "http://localhost:5023/mcp" } } }

Now wire it up in the editor:

  1. Make sure your app is running (dotnet run).
  2. Open .vscode/mcp.json. A Start code-lens appears above the quizzes server — click it. (Or run MCP: List Servers from the Command Palette and start it there.)
  3. The server status should go to Running and report 4 tools.
Start the API first An http MCP server in mcp.json connects to a URL you're responsible for hosting. If dotnet run isn't up, VS Code can't connect. (Contrast with stdio servers, which VS Code launches for you.)
06

Drive it from the agent

  1. Open the Copilot Chat view and switch the mode selector to Agent.
  2. Click the tools (wrench) icon — your list_quizzes, get_quiz, create_quiz, add_question tools are listed under the quizzes server. Make sure they're enabled.
  3. Ask it to do something. The agent picks the tools itself:
"What quizzes do I have?" "Create a quiz called 'REST basics' with a short description, then add three good questions to it." "Add a question to the HTTP basics quiz about status codes."

The first time a tool runs, VS Code asks you to confirm the invocation — you're letting the agent execute real code. Approve it.

The payoff After the agent creates a quiz, switch to Swagger or run curl http://localhost:5023/quizzes. The agent's quiz is there — it went through the same IQuizRepository into the same SQL Server table. The AI and your API are writing to one database.
07

How it works & what to watch for

  • One process, two faces. The same app serves REST (for humans/clients) and MCP (for agents). Both go through IQuizRepository — the abstraction from Lab 5 pays off a third time.
  • Descriptions are the API for the model. Vague [Description] text → the agent misuses or ignores the tool. Treat them like prompt engineering: say what the tool does, what each argument means, and what comes back.
  • Stdio vs Streamable HTTP. A stdio server is a process the host launches and talks to over standard in/out — great for a personal, local tool. Streamable HTTP is a networked endpoint multiple clients can reach — closer to how you'd actually ship one.
Security — this is a dev setup Our /mcp endpoint has no authentication, and the tools mutate your database. That's fine on localhost for a lab. A real Streamable HTTP MCP server needs auth (the spec uses OAuth), authorization on each tool, and validation — an agent will call your tools with whatever arguments it infers.
Where this could go Add a generate_quiz tool that uses an LLM to draft questions and persists them; expose delete_quiz (and feel the need for confirmation/auth); or return response DTOs instead of entities. You now have a clean seam between your data and any agent that wants to use it.

You shipped an MCP server.

Your Quizzes API now speaks two protocols: REST for clients and MCP for agents, over Streamable HTTP, sharing one database through one repository. Lab 2 consumed tools; today you produced them.
