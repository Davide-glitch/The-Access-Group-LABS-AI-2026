Give the Quizzes API a real memory

The API you have forgets everything when it restarts. In this lab you'll back it with SQL Server through Entity Framework Core — a DbContext, migrations, an EF-backed repository — convert it to async, and model a one-to-many relationship. The controller barely changes, because Lab 5 hid storage behind an interface.

02

Create the DbContext and seed data

The DbContext is your session with the database. It exposes a DbSet<T> per table and is where we describe the model. Create a Data folder and add:

Data/QuizzesDbContext.cs
using Lab6.Models; using Microsoft.EntityFrameworkCore; namespace Lab6.Data; public class QuizzesDbContext : DbContext { public QuizzesDbContext(DbContextOptions<QuizzesDbContext> options) : base(options) { } public DbSet<Quiz> Quizzes => Set<Quiz>(); protected override void OnModelCreating(ModelBuilder modelBuilder) { // Seed rows, applied by a migration. Fixed GUIDs + fixed timestamp so the // seed is deterministic and migrations don't keep detecting "changes". var seededAt = new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc); modelBuilder.Entity<Quiz>().HasData( new Quiz { Id = Guid.Parse("11111111-1111-1111-1111-111111111111"), Title = "C# fundamentals", Description = "Variables, types, control flow, methods.", CreatedAt = seededAt }, new Quiz { Id = Guid.Parse("22222222-2222-2222-2222-222222222222"), Title = "HTTP basics", Description = "Verbs, status codes, headers.", CreatedAt = seededAt }, new Quiz { Id = Guid.Parse("33333333-3333-3333-3333-333333333333"), Title = "REST principles", Description = "Resources, idempotency, anti-patterns.", CreatedAt = seededAt }); } }
Why fixed GUIDs and a fixed timestamp in the seed? HasData seed rows must be deterministic. If you used Guid.NewGuid() or DateTime.UtcNow here, every dotnet ef migrations add would see different values and try to re-seed. Hard-coded values keep the seed stable across migrations.
Why DbSet<Quiz> Quizzes => Set<Quiz>() instead of a property with a setter? It's the modern, null-safe way to declare a DbSet. Set<Quiz>() asks the context for the set; the expression-bodied property avoids a nullable warning you'd get from public DbSet<Quiz> Quizzes { get; set; }.

Register the DbContext in DI

Open Program.cs. Add the EF usings, read the connection string, and register the context. The highlighted lines are new:

Leave the rest of Program.cs (the pipeline and app.Run()) unchanged.

Verify dotnet build succeeds. The app still uses the in-memory store — we've only registered the context so the migration tooling can find it.
04

Create and apply the first migration

A migration is the C# diff between your model and the database. The first one builds the whole schema from scratch.

# generate the migration code dotnet ef migrations add InitialCreate # apply it: creates the QuizzesDb database, the Quizzes table, and the seed rows dotnet ef database update

You now have a Migrations/ folder with <timestamp>_InitialCreate.cs. Open it and read the Up() method.

Read the migration before you trust it Up() is the exact set of operations applied to your database — a CreateTable for Quizzes and three InsertData calls for the seed. Down() reverses them. This file is checked into source control; it's how every environment gets the same schema.
Verify database update ends with Done. A new __EFMigrationsHistory table now records which migrations have run, so EF never applies the same one twice.

06

Write the EF repository — and swap one line

Here's the payoff for Lab 5's interface. We write a new implementation of IQuizRepository backed by the context. Same five methods, real storage.

Repositories/EfQuizRepository.cs
using Lab6.Data; using Lab6.Models; namespace Lab6.Repositories; public class EfQuizRepository : IQuizRepository { private readonly QuizzesDbContext _db; public EfQuizRepository(QuizzesDbContext db) => _db = db; public IEnumerable<Quiz> All() => _db.Quizzes.OrderBy(q => q.CreatedAt).ToList(); public Quiz? Find(Guid id) => _db.Quizzes.Find(id); public Quiz Add(string title, string? description) { var quiz = new Quiz { Title = title, Description = description }; _db.Quizzes.Add(quiz); _db.SaveChanges(); return quiz; } public bool Update(Guid id, string title, string? description) { var existing = _db.Quizzes.Find(id); if (existing is null) return false; existing.Title = title; existing.Description = description; _db.SaveChanges(); return true; } public bool Remove(Guid id) { var existing = _db.Quizzes.Find(id); if (existing is null) return false; _db.Quizzes.Remove(existing); _db.SaveChanges(); return true; } }

Now the swap. In Program.cs, change the registration:

// before builder.Services.AddSingleton<IQuizRepository, InMemoryQuizRepository>(); // after builder.Services.AddScoped<IQuizRepository, EfQuizRepository>();

The in-memory class is now unused. Delete it:

rm Repositories/InMemoryQuizRepository.cs
Why Scoped, not Singleton? A DbContext is not thread-safe and is meant to be short-lived — one per HTTP request. AddDbContext already registers the context as Scoped, so the repository that depends on it must be Scoped too. A Singleton repository holding a Scoped context would blow up (or corrupt state) under concurrent requests.
The point Look at QuizzesController.cs. You did not touch it. The controller depends on IQuizRepository; swapping the implementation is invisible to it. That's what the interface bought you.

08

Make the data access async

Database calls are I/O. Blocking a thread while SQL Server works wastes it. The web-API norm is async/await end to end, so the thread is freed to serve other requests. EF Core has async versions of every query.

We'll change three files: the interface, the repository, and the controller.

1. The interface — every method returns a Task:

Repositories/IQuizRepository.cs
using Lab6.Models; namespace Lab6.Repositories; public interface IQuizRepository { Task<IEnumerable<Quiz>> AllAsync(); Task<Quiz?> FindAsync(Guid id); Task<Quiz> AddAsync(string title, string? description); Task<bool> UpdateAsync(Guid id, string title, string? description); Task<bool> RemoveAsync(Guid id); }

2. The repository — await the EF async methods:

Repositories/EfQuizRepository.cs
using Lab6.Data; using Lab6.Models; using Microsoft.EntityFrameworkCore; namespace Lab6.Repositories; public class EfQuizRepository : IQuizRepository { private readonly QuizzesDbContext _db; public EfQuizRepository(QuizzesDbContext db) => _db = db; public async Task<IEnumerable<Quiz>> AllAsync() => await _db.Quizzes.OrderBy(q => q.CreatedAt).ToListAsync(); public async Task<Quiz?> FindAsync(Guid id) => await _db.Quizzes.FindAsync(id); public async Task<Quiz> AddAsync(string title, string? description) { var quiz = new Quiz { Title = title, Description = description }; _db.Quizzes.Add(quiz); await _db.SaveChangesAsync(); return quiz; } public async Task<bool> UpdateAsync(Guid id, string title, string? description) { var existing = await _db.Quizzes.FindAsync(id); if (existing is null) return false; existing.Title = title; existing.Description = description; await _db.SaveChangesAsync(); return true; } public async Task<bool> RemoveAsync(Guid id) { var existing = await _db.Quizzes.FindAsync(id); if (existing is null) return false; _db.Quizzes.Remove(existing); await _db.SaveChangesAsync(); return true; } }

3. The controller — each action becomes async Task<...> and awaits the repo:

Controllers/QuizzesController.cs
[HttpGet] public async Task<ActionResult<IEnumerable<Quiz>>> List() => Ok(await _repo.AllAsync()); [HttpGet("{id:guid}", Name = nameof(GetById))] public async Task<ActionResult<Quiz>> GetById(Guid id) { var quiz = await _repo.FindAsync(id); return quiz is null ? NotFound() : Ok(quiz); } [HttpPost] public async Task<ActionResult<Quiz>> Create(CreateQuizDto dto) { var quiz = await _repo.AddAsync(dto.Title, dto.Description); return CreatedAtAction(nameof(GetById), new { id = quiz.Id }, quiz); } [HttpPut("{id:guid}")] public async Task<IActionResult> Replace(Guid id, UpdateQuizDto dto) { var updated = await _repo.UpdateAsync(id, dto.Title, dto.Description); return updated ? NoContent() : NotFound(); } [HttpDelete("{id:guid}")] public async Task<IActionResult> Delete(Guid id) => await _repo.RemoveAsync(id) ? NoContent() : NotFound();
Verify dotnet build is clean, and the API behaves identically in Swagger. Nothing changed for the client — async is an internal efficiency, not a contract change.
No migration needed here Async changed code, not the model. The database schema is untouched, so there's nothing to migrate.
09

Add Questions — a one-to-many relationship

A quiz has many questions; a question belongs to one quiz. We model that with a new entity, a foreign key, and navigation properties on both sides.

1. The new model:

Models/Question.cs
using System.Text.Json.Serialization; namespace Lab6.Models; public class Question { public Guid Id { get; set; } = Guid.NewGuid(); public string Text { get; set; } = ""; // foreign key + navigation back to the owning quiz public Guid QuizId { get; set; } [JsonIgnore] // break the Quiz -> Questions -> Quiz serialization cycle public Quiz? Quiz { get; set; } }

2. The collection on Quiz (add the last line):

Models/Quiz.cs
public DateTime CreatedAt { get; set; } = DateTime.UtcNow; public List<Question> Questions { get; set; } = [];

3. Expose the table on the context (add below the Quizzes set):

Data/QuizzesDbContext.cs
public DbSet<Quiz> Quizzes => Set<Quiz>(); public DbSet<Question> Questions => Set<Question>();

4. A validated input DTO:

Dtos/CreateQuestionDto.cs
using System.ComponentModel.DataAnnotations; namespace Lab6.Dtos; public class CreateQuestionDto { [Required] [StringLength(500, MinimumLength = 3)] public string Text { get; set; } = ""; }

5. Add to the interface:

// add to IQuizRepository Task<Quiz?> AddQuestionAsync(Guid quizId, string text);

6. Implement it, and pull questions in when reading a quiz. Add the method, add .Include(...) to AllAsync, and switch FindAsync to load the children:

Repositories/EfQuizRepository.cs
public async Task<IEnumerable<Quiz>> AllAsync() => await _db.Quizzes .Include(q => q.Questions) .OrderBy(q => q.CreatedAt).ToListAsync(); public async Task<Quiz?> FindAsync(Guid id) => await _db.Quizzes .Include(q => q.Questions) .FirstOrDefaultAsync(q => q.Id == id); public async Task<Quiz?> AddQuestionAsync(Guid quizId, string text) { var quizExists = await _db.Quizzes.AnyAsync(q => q.Id == quizId); if (!quizExists) return null; _db.Questions.Add(new Question { Text = text, QuizId = quizId }); await _db.SaveChangesAsync(); return await _db.Quizzes .Include(q => q.Questions) .FirstOrDefaultAsync(q => q.Id == quizId); }
The Guid-key trap — why we Add the question explicitly Our Question.Id is set in C# (= Guid.NewGuid()), but EF's convention treats Guid keys as store-generated. If you add a new question through the parent's collection (quiz.Questions.Add(...)), EF can mistake the already-populated key for an existing row and emit an UPDATE — which matches zero rows and throws a DbUpdateConcurrencyException. Calling _db.Questions.Add(...) explicitly forces an INSERT. (Setting the key to ValueGeneratedNever in OnModelCreating is the other fix.)

7. The endpoint — a nested route under a quiz:

Controllers/QuizzesController.cs
[HttpPost("{id:guid}/questions")] public async Task<ActionResult<Quiz>> AddQuestion(Guid id, CreateQuestionDto dto) { var quiz = await _repo.AddQuestionAsync(id, dto.Text); return quiz is null ? NotFound() : Ok(quiz); }
Why [JsonIgnore] on Question.Quiz? Returning the EF entity directly, a Quiz serializes its Questions, and each Question would serialize its Quiz back — an infinite loop the JSON serializer rejects. Ignoring the back-reference breaks the cycle. (In a larger app you'd return a dedicated response DTO instead of the entity — the same lesson as Lab 5's input DTOs, applied to output.)
10

Second migration, then test the relationship

The model changed, so add a migration. Watch how small it is — EF only emits the diff.

dotnet ef migrations add AddQuestions dotnet ef database update

Open the generated <timestamp>_AddQuestions.cs. Its Up() contains a single CreateTable("Questions") with a foreign key to Quizzes — it does not recreate the Quizzes table. That's the power of migrations: each one is just the change since the last.

Now exercise it in Swagger:

# 1. create a quiz, copy its id from the response POST /quizzes {"title":"HTTP deep dive","description":"verbs and codes"} # 2. add a question to it (use the id in the path) POST /quizzes/{id}/questions {"text":"What makes PUT idempotent?"} # 3. read the quiz back — it now carries its questions array GET /quizzes/{id}
Verify Step 3 returns the quiz with a populated questions array and no serialization error. Posting a question to a non-existent quiz id returns 404. Restart the app and the quiz and its question are still there.
Cascade delete comes for free Because QuizId is non-nullable, EF makes the relationship required and configures cascade delete by default — deleting a quiz removes its questions automatically. You can confirm the onDelete: Cascade in the migration's foreign-key definition.
11

Homework — take it further

You have a persisted, async API with a one-to-many relationship. Extend it. Make each decision deliberately and note your choices in a short README.md next to your code.

Pick at least two:

  • Full CRUD on questions. Add GET, PUT, and DELETE for individual questions. Decide the URL shape: nested (/quizzes/{id}/questions/{qid}) or top-level (/questions/{qid}) — and justify it.
  • Response DTOs. Stop returning EF entities. Introduce QuizResponse / QuestionResponse DTOs and map to them, removing the need for [JsonIgnore]. This is the "proper" fix the guide hinted at.
  • Tags — a many-to-many relationship. Add a Tag entity and let a quiz have many tags while a tag applies to many quizzes. Add skip navigations (Quiz.Tags and Tag.Quizzes) and let EF infer the join table, then add a migration. Expose POST /quizzes/{id}/tags to attach a tag (creating it if new) and GET /quizzes?tag=… to filter. A genuinely different relationship shape from Questions.
  • Richer questions. Add multiple-choice options and a correct answer. That's another one-to-many (Question → Options) and another migration.
  • Pagination. Make GET /quizzes take ?page=&pageSize= and use Skip/Take. What's a sensible default and maximum page size?
  • Move secrets out of config. If you used the Docker fallback, move the password into user-secrets (dotnet user-secrets) instead of appsettings.json.
Migration discipline Every model change needs its own migration. Never edit a migration that's already been applied and shared — add a new one. Treat Migrations/ like any other source code: commit it.
Stretch goal Add POST /quizzes/{id}/attempts: the client submits answers, the server scores them against the stored questions and returns the result. Now your persisted data is doing real work — and the door is open to an AI endpoint that generates a quiz and writes it straight into the database.
