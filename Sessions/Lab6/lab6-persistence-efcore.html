Part 1 · The problem

In-memory means amnesia

The in-memory repo keeps quizzes in a ConcurrentDictionary. That dictionary lives in RAM, inside the process.

The moment the app stops — a deploy, a crash, a machine reboot, even Ctrl+C in development — every quiz your users created is gone. Back to the three seeded rows.

Run two copies behind a load balancer and it's worse: each has its own dictionary. A quiz created on server A doesn't exist on server B.

We need state that outlives the process and is shared across instances. That's a database.

RAM

Fast, but volatile and per-process. Perfect for a cache, fatal for a system of record.

Database

Durable, shared, queryable, transactional. Survives restarts and scales across servers.

# restart the app... GET /quizzes [ "C# fundamentals", "HTTP basics", "REST principles" ] # your 47 created quizzes? gone.
Part 1 · Concepts

An ORM maps objects to tables

A relational database speaks tables, rows, and SQL. Your code speaks classes, objects, and properties. An Object-Relational Mapper bridges the two.

Entity Framework Core is .NET's ORM. You write LINQ over C# objects; it generates the SQL, runs it, and turns rows back into objects.

The alternative — hand-writing SQL strings with ADO.NET — is still valid and sometimes faster, but it's verbose and easy to get wrong. EF Core is the default starting point in .NET.

C# objectnew Quiz { Title = "REST" }
↕   EF Core maps
table rowQuizzes(Id, Title, Description, CreatedAt)

What EF Core does for you

  • Generates CREATE TABLE and CRUD SQL
  • Translates LINQ into SQL queries
  • Tracks changes and batches them into one save
  • Manages connections and transactions
Part 1 · Concepts

The four pieces of EF Core

DbContext

Your session with the database. One per request. Holds the connection, the change tracker, and your DbSets. You'll write QuizzesDbContext.

DbSet<T>

A table, as a queryable collection. DbSet<Quiz> Quizzes is "the Quizzes table". You Add, Remove, and LINQ over it.

Change tracker

Watches the entities the context loaded, notices what you modified, and works out the minimal INSERT/UPDATE/DELETE on SaveChanges.

Provider

The database-specific plug-in that emits the right SQL dialect. We use the SQL Server provider; swapping to Postgres or SQLite is mostly a package change.

Mental model: a DbContext is a short-lived workspace. Load things, poke at them, save, dispose.

Part 1 · Concepts

SaveChanges is one unit of work

You don't write SQL per change. You mutate tracked objects, then call SaveChanges() once. EF Core diffs the tracked state and sends everything in a single transaction.

Either all of it commits, or none of it does. That's the unit of work pattern, for free.

The #1 beginner trap

You changed an object but the database didn't update. You forgot to call SaveChanges(). Tracking is not saving.

var quiz = ctx.Quizzes.Find(id); // tracked quiz.Title = "REST, revised"; // tracker notices ctx.Quizzes.Add(newQuiz); // pending insert ctx.Quizzes.Remove(oldQuiz); // pending delete ctx.SaveChanges(); // one transaction: 1 UPDATE + 1 INSERT + 1 DELETE
Part 2 · Setup

Which SQL Server?

LocalDB  we use this

A lightweight, on-demand SQL Server that ships with Visual Studio. Zero setup, file-based, Windows-only.

(localdb)\MSSQLLocalDB

Docker  fallback

Full SQL Server in a container. Cross-platform — the option for Mac/Linux or anyone without LocalDB.

localhost,1433

Full / Express

A real installed instance, or Azure SQL in production. Same provider, same code — only the connection string changes.

The beauty: your C# doesn't change between these. The provider and connection string absorb the difference. The baseline ships with the LocalDB string already in appsettings.json; the Docker command and string are in the README.

Part 2 · Setup

Connection strings live in config

A connection string tells the provider where the server is and how to authenticate. It belongs in appsettings.json, read by name — never hard-coded in C#.

  • Server — the instance to reach
  • Database — created on first migration if absent
  • Trusted_Connection — use your Windows login (LocalDB)
  • TrustServerCertificate — accept the dev cert locally

Don't commit real secrets

LocalDB needs no password, so it's git-safe. For Docker/production, keep passwords in user-secrets or environment variables, not source.

// appsettings.json (already in the baseline) "ConnectionStrings": { "QuizzesDb": "Server=(localdb)\\MSSQLLocalDB; Database=QuizzesDb; Trusted_Connection=True; TrustServerCertificate=True" }
Part 3 · Migrations

Your model is the source of truth

You don't hand-write CREATE TABLE. You define C# classes; EF Core compares them to a snapshot of the last known schema and generates a migration — the diff needed to bring the database in line.

Each migration is a checked-in C# file with Up() (apply) and Down() (revert). They're ordered, they're versioned, and they're how the schema evolves safely over a project's life.

Change a model → add a migration → update the database. Every time.

C# modelclass Quiz { ... }
↓   migrations add
migration fileUp() / Down() — the diff
↓   database update
SQL Server schematables actually created
Part 3 · Migrations

The dotnet ef workflow

Migrations are driven by a CLI tool you install once per machine, plus two packages in the project.

  • Microsoft.EntityFrameworkCore.SqlServer — the provider
  • Microsoft.EntityFrameworkCore.Design — powers the tooling

Then it's a tight loop: add a migration when the model changes, apply it to the database.

Read before you apply

Open the generated migration and actually look at the Up() method. It's the contract for what hits your database.

# once per machine dotnet tool install --global dotnet-ef # add packages dotnet add package Microsoft.EntityFrameworkCore.SqlServer dotnet add package Microsoft.EntityFrameworkCore.Design # the loop, every time the model changes dotnet ef migrations add InitialCreate dotnet ef database update
Part 4 · The swap

This is why we built an interface

The controller depends on IQuizRepository, never on a concrete class. So a database-backed implementation is a drop-in.

We write a new EfQuizRepository that implements the same interface, then change one line of DI registration. The controller, the DTOs, the routes — untouched.

Note the lifetime change: an in-memory store is a Singleton; a DbContext-backed repo must be Scoped — one per request.

// before — volatile, one shared instance builder.Services.AddSingleton<IQuizRepository, InMemoryQuizRepository>(); // after — durable, one per request builder.Services.AddScoped<IQuizRepository, EfQuizRepository>(); // the controller never changed.
Part 5 · Async

Database calls should be async

A query to SQL Server is I/O — your thread would otherwise sit blocked, waiting on the network and disk, doing nothing.

With async/await, the thread is released to serve other requests while the database works. Same hardware, far more throughput. This is the norm for web APIs.

EF Core exposes async versions of everything: ToListAsync, FindAsync, SaveChangesAsync. We'll thread Task through the interface, the repo, and the controller.

// sync — thread blocks on I/O Quiz? Find(Guid id); var all = ctx.Quizzes.ToList(); // async — thread freed while DB works Task<Quiz?> FindAsync(Guid id); var all = await ctx.Quizzes.ToListAsync(); await ctx.SaveChangesAsync();

Hands-on · brief

The DbContext and seed data

One class with a DbSet per table. Seed data moves out of the repo constructor and into OnModelCreating via HasData — so it's applied by a migration, with stable IDs.

Why fixed GUIDs in the seed?

Seed rows need deterministic keys, or every migration would think the data changed. Hard-code the GUIDs for seeded quizzes.

public class QuizzesDbContext : DbContext { public QuizzesDbContext(DbContextOptions o) : base(o) { } public DbSet<Quiz> Quizzes => Set<Quiz>(); protected override void OnModelCreating(ModelBuilder b) => b.Entity<Quiz>().HasData(/* seeded rows */); }
Hands-on · brief

Register the context in DI

AddDbContext wires the context into the container as a Scoped service and tells it which provider and connection string to use.

Now the EfQuizRepository can ask for a QuizzesDbContext in its constructor — DI hands it a fresh one per request and disposes it after.

var cs = builder.Configuration .GetConnectionString("QuizzesDb"); builder.Services.AddDbContext<QuizzesDbContext>( opt => opt.UseSqlServer(cs)); builder.Services.AddScoped<IQuizRepository, EfQuizRepository>();
Hands-on · brief

Create the schema, then look at it

Run the two commands. migrations add writes the C# diff; database update connects to LocalDB, creates the QuizzesDb database, the Quizzes table, and inserts the seed rows.

Then open SSMS or Azure Data Studio, connect to (localdb)\MSSQLLocalDB, and see your table and rows with your own eyes.

dotnet ef migrations add InitialCreate # -> Migrations/..._InitialCreate.cs dotnet ef database update # -> Applying migration... # -> Done. DB + table + seed rows exist. # a __EFMigrationsHistory table now # records which migrations have run.
Hands-on · brief

The EF-backed repository

Same interface, real storage. The context comes in through the constructor; each method becomes a LINQ query plus, for writes, a SaveChanges.

Then flip the one DI line from InMemory to Ef. Run the app — same Swagger, same endpoints, but the data is now in SQL Server.

public class EfQuizRepository : IQuizRepository { private readonly QuizzesDbContext _db; public EfQuizRepository(QuizzesDbContext db) => _db = db; public IEnumerable<Quiz> All() => _db.Quizzes.OrderBy(q => q.CreatedAt).ToList(); // Find / Add / Update / Remove + SaveChanges... }
Hands-on · brief

Questions: a one-to-many relationship

A quiz has many questions; a question belongs to one quiz. In relational terms that's a foreign key. In EF terms it's a navigation property.

EF infers the relationship from the QuizId + Quiz properties and the List<Question> on the other side. This is what a dictionary could never give you cleanly.

Add the model, then a second migration — watch it generate only the diff: a new table and FK.

public class Question { public Guid Id { get; set; } = Guid.NewGuid(); public string Text { get; set; } = ""; // foreign key + navigation public Guid QuizId { get; set; } public Quiz? Quiz { get; set; } } // on Quiz: public List<Question> Questions { get; set; } = [];
Hands-on · the payoff

Restart the app. Data's still there.

The whole point, in one experiment:

  • POST a new quiz with a couple of questions
  • Stop the app entirely (Ctrl+C)
  • Start it again
  • GET /quizzes — your quiz is still there

That's persistence. The data outlived the process — because it lives in SQL Server now, not in RAM.

# before: in-memory GET /quizzes (after restart) [ seeded only — your data gone ] # after: EF + SQL Server GET /quizzes (after restart) [ seeded + everything you created ]
Watch out

Things people get wrong on day one

  • Forgetting SaveChanges — you changed objects, nothing persisted. Tracking is not saving.
  • Changing a model but not adding a migration — runtime error: the model and database disagree.
  • Registering the context or repo as Singleton — a DbContext is not thread-safe. It must be Scoped.
  • Returning EF entities straight from the API and triggering the N+1 problem, or serializing a navigation-property cycle. Keep using DTOs.
  • Editing an already-applied migration by hand. Don't — add a new migration instead.
  • Committing a Docker/production password in the connection string. Use user-secrets or env vars.
Wrap-up

What you can do now

You took an API that forgot everything on restart and gave it durable, shared, queryable storage — without touching the controller.

  • Model data as C# and map it to SQL Server with EF Core
  • Evolve a schema safely with migrations
  • Swap implementations behind an interface
  • Write async data access
  • Model a one-to-many relationship

Where this goes next

Real persistence unlocks the rest of a production API: authentication tied to stored users, pagination and filtering over real tables, integration tests against a database, and deployment to a hosted SQL Server.
