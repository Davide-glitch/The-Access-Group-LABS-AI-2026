Where we are

The API trusts everyone

Lab 6 left us with a persisted Quizzes API. It works — but it has no idea who is calling.

Any caller can POST a quiz, PUT over anyone else's, or DELETE the lot. There's no concept of an account, and no concept of mine vs yours.

A real API needs to know who you are, and decide what you're allowed to touch.

# anyone, no sign-in required DELETE /quizzes/1111... 204 No Content # ...that was someone else's quiz. # nothing stopped them.
The core idea

Two different questions

Authentication — who are you?

Proving identity. The caller presents a credential (here, a token from Microsoft) and the API verifies it. Either we know who you are, or we don't.

Fails → 401 Unauthorized

Authorization — are you allowed?

Given that we know who you are, deciding whether you may do this to this thing. Editing a quiz you own: yes. Someone else's: no.

Fails → 403 Forbidden

Authentication is the cheap part today — Microsoft does the hard work. Authorization, specifically ownership, is the real lesson.

Concepts · authentication

A token is your proof of identity

APIs are stateless — there's no session cookie holding your login. Instead, the caller attaches a token to every request, in the Authorization header:

Authorization: Bearer <token>

"Bearer" means whoever holds it is treated as the user — like cash. The API checks the token is genuine and unexpired, and reads who you are from it. No database lookup of a password, every request.

The big question: where does that token come from, and how do we trust it? That's OAuth.

GET /quizzes Authorization: Bearer eyJ0eXAi...9.eyJvaWQ... ↓ # API: signature valid? issuer + audience # ours? not expired? → yes 200 OK
Concepts · authentication

OAuth: don't handle passwords yourself

We never see the user's password. We delegate sign-in to Microsoft and get back a token. The browser does a redirect dance — the authorization code flow:

1 · Swaggerredirects you to Microsoft to sign in
→
2 · Microsoftyou log in & consent; it returns a one-time code
→
3 · Swaggerswaps the code (+ PKCE) for an access token
→
4 · APIgets the token on each call & validates it

PKCE — no secret needed

Swagger runs in a browser and can't keep a secret. PKCE secures the code exchange with a one-time proof instead. That's why this lab ships no passwords or client secrets anywhere.

OIDC adds identity

OAuth was built for authorization; OpenID Connect layers identity on top — a standard set of claims about who the user is. That's where your user id comes from.

Concepts · authentication

What's inside the token: claims

Microsoft issues a JWT — a signed JSON object of claims (facts about the user and the token). Anyone can read it; only Microsoft can sign it, so it can't be forged.

The API validates the signature against Microsoft's public keys, checks the aud (audience) is us and it hasn't expired, then exposes the claims as User.

The one claim that matters today: oid

The object id — stable and unique per user, and it never changes. Unlike a name or email, it's safe to use as a key. This becomes the owner of every quiz.

// decoded JWT payload (jwt.ms) { "aud": "5c2ab77a-...-327f600296e6", // us "iss": "https://login.microsoft...", "oid": "a1b2c3d4-....", // ← the user "name": "Ada Lovelace", "preferred_username": "ada@outlook.com", "exp": 1718000000 // expiry }

Personal accounts consumers

Sign in with any outlook.com/hotmail.com account. No work account, no corporate IT, no admin consent. Everyone can get one in a minute.

No front-end yet — so Swagger's Authorize button runs the sign-in flow and attaches the token to every call. Next week's UI reuses the same setup.

Our approach

The API just validates — that's it

For an API, authentication is surprisingly little code. We don't issue tokens, store passwords, or manage users — Microsoft does all of that.

Microsoft.Identity.Web adds one authentication handler that checks every incoming token: signature, issuer, audience, expiry. Valid → User is populated. Invalid or missing → 401.

The config is three values in appsettings.json — the same ones your instructor hands out.

// Program.cs — the whole of authentication builder.Services .AddAuthentication(JwtBearerDefaults.AuthenticationScheme) .AddMicrosoftIdentityWebApi( builder.Configuration.GetSection("AzureAd")); // appsettings.json "AzureAd": { "Instance": "https://login.microsoftonline.com/", "TenantId": "consumers", "ClientId": "<client-id>" }
Concepts · the two failures

401 vs 403 — learn the difference

401 Unauthorized

"I don't know who you are." No token, an expired one, or one we can't validate. The fix is to authenticate — sign in and try again.

403 Forbidden

"I know exactly who you are — and you still can't do this." You're signed in, but it's not your resource. Signing in again won't help.

Editing someone else's quiz is the textbook 403: authenticated, not permitted. In code, Forbid() returns 403; Unauthorized() returns 401. The [Authorize] attribute produces the 401 for you automatically.

Concepts · authorization

Two levels of "are you allowed?"

Endpoint-level — before the action

"Can you call this at all?" Expressed with the [Authorize] attribute (optionally roles/policies). It runs before the action, and knows nothing about a specific row.

Resource-level — after you load the row

"Can you do this to this object?" Depends on the data — who owns this quiz. You can't answer it with an attribute, because the quiz hasn't been loaded yet.

Ownership is inherently resource-level. The check has to happen inside the action, after fetching the quiz:

// load first — only then can you check ownership var quiz = await _repo.FindAsync(id); if (quiz is null) return NotFound(); if (quiz.OwnerId != User.GetObjectId()) return Forbid(); // 403
Concepts · authorization

The ownership model

Three small moves turn "anyone can edit anything" into "only the owner can":

  • Add an OwnerId column to Quiz
  • On create, stamp it with the caller's oid
  • On update/delete, compare OwnerId to the caller — 403 if they differ

GET stays open to any signed-in user — ownership governs mutation, not visibility.

POST /quizzesOwnerId = your oid (from the token)
↓
PUT / DELETEquiz.OwnerId == your oid?
↓
yes → 204  ·  no → 403only the owner mutates

Question for the room: that "caller's oid" — where does it come from, and could a client just send whatever owner id it wants? →

The cardinal rule

Identity comes from the token, never the body

The owner is read from the validated token (oid) — server-side, where the client can't touch it.

It is never a field on the request body. If the client could send ownerId, anyone could claim to be anyone — the whole model collapses.

Notice OwnerId is not on CreateQuizDto. That's deliberate.

[HttpPost] public async Task<...> Create(CreateQuizDto dto) { // from the token, not the body var ownerId = User.GetObjectId()!; var quiz = await _repo.AddAsync( dto.Title, dto.Description, ownerId); ... }
A neat testing trick

Seeded quizzes belong to "the house"

The three demo quizzes are seeded with a fixed owner id that no real person has — ...feed.

So you can prove the whole rule with just your own account: a quiz you create is yours (edit → 204), and a seeded quiz is someone else's (edit → 403).

The 403 is success, not a bug. No second account, no partner needed.

Hands-on · brief

Lock the controller, watch it reject you

One attribute on the controller requires a valid token for every action. Then two middleware lines turn it on — in the right order.

Order matters

UseAuthentication (who are you) must come before UseAuthorization (are you allowed). Reverse them and you get baffling 401s. The classic mistake.

[ApiController] [Route("quizzes")] [Authorize] // ← every action needs a token public class QuizzesController ... // Program.cs, after Swagger, before MapControllers app.UseAuthentication(); // 1. who are you? app.UseAuthorization(); // 2. are you allowed?

Add the owner, then a migration

Watch out

Things people get wrong on day one

  • Middleware order — UseAuthorization before UseAuthentication. Auth must come first, both before MapControllers.
  • Changing the port — the sign-in redirect URI is registered for localhost:5023 exactly. A different port breaks the login popup.
  • Trusting the client for identity — reading ownerId from the request body instead of User.GetObjectId(). Never.
  • Checking ownership with an attribute — you can't; the row isn't loaded yet. The check lives inside the action, after the fetch.
  • Confusing 401 and 403 — "not signed in" vs "signed in but not yours". They mean different things; return the right one.
  • Forgetting [Authorize] — an endpoint with no attribute is wide open, even with auth configured.
