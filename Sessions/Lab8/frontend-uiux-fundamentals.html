Concepts · the frontend

Where your code runs: the browser

A web app has two halves. The backend runs on a server: it owns the database, enforces rules, and answers requests with data (JSON). It has no idea what anything looks like.

The frontend runs in each user's browser. It turns that data into pixels, and reacts to clicks and typing. The two talk over HTTP.

Backend on a server

Owns data, auth, business rules. Speaks JSON. One copy, shared by everyone.

↕ HTTP request / response

Frontend in the browser

Renders the UI, handles interaction. Runs fresh in every visitor's browser.

Step 5 is where today's apps live: the page loads once, then JavaScript fetches data and updates the screen without a full reload. That's a "single-page app" — what React builds.

Concepts · the building materials

HTML, CSS, JavaScript — three jobs

  • HTML — structure: the elements and their meaning.
  • CSS — style: colour, spacing, layout, type.
  • JavaScript — behaviour: what happens on click, type, load.

Keep them separate in your head even when a framework blends them: a thing's meaning, its look, and its behaviour are three different decisions.

<!-- HTML: structure --> <button class="run">Run quiz</button> /* CSS: style */ .run { background: #2563eb; color: white; padding: .6em 1em; border-radius: 8px; } // JavaScript: behaviour btn.addEventListener('click', startQuiz);
Concepts · the page as data

The DOM: your page as a live tree

The browser parses your HTML into the DOM — a tree of objects it can change at runtime. Every visible thing is a node.

Plain JS means you find nodes and update them by hand — fine for one button, painful for a whole app, where the screen and your data drift apart. Frameworks like React keep the DOM in sync with your data for you.

Concepts · many screens

One site, every screen

Your interface is viewed on phones, tablets, laptops and huge monitors. Responsive design means one layout that adapts — not a separate site per device.

  • Mobile-first — design the small screen first, then add for bigger.
  • Fluid layouts — relative sizes (%, rem) over fixed pixels.
  • Breakpoints — rules that rearrange the layout at certain widths.

Rule of thumb

If it works on a narrow phone, it almost always works on a wide screen — rarely the reverse. Start narrow. Touch targets need room (≈44px); text needs to stay readable without zooming.

Design · the big distinction

UX vs UI — not the same thing

UX — User Experience

The whole journey: can people accomplish their goal? Is the flow logical, fast, and frustration-free? It's about how it works — structure, flow, content.

UI — User Interface

The surface they touch: buttons, type, colour, spacing, motion. It's about how it looks and feels — the visual and interactive layer on top of the UX.

Beautiful but confusing fails. Clear but ugly frustrates. You need both — UX decides the bones, UI dresses them.

Design · the mindset

Design is for the user, not the designer

Good design starts from what people are trying to do — not from what looks impressive. It's a loop, not a one-shot:

Researchwho, what goal, what context
→
Designsketch the flow & screens
→
Prototypemake it clickable
→
Testwatch real people use it
→
Iteratefix what tripped them up

You are not your user. The fastest way to find a bad design is to watch someone else try to use it.

Design · guide the eye

Visual hierarchy: what gets noticed first

Every screen answers a silent question: where do I look first? You control that with size, weight, colour, and position.

Make the most important thing the most prominent. If everything shouts, nothing is heard — one clear primary action per screen.

In practice

  • Big, bold heading → the page's purpose
  • One primary button; secondary actions quieter
  • Group related things; separate unrelated ones
  • Use whitespace to say "these belong together"
Design · arranging things

Four habits that make layouts look intentional

Contrast

Make different things look clearly different — size, colour, weight. Contrast creates hierarchy and draws attention.

Repetition

Reuse the same styles for the same kinds of thing. Consistency is what makes a UI feel like one product.

Alignment

Line things up on a shared edge. Invisible grids are why "clean" designs look calm rather than scattered.

Proximity

Put related items close, unrelated items apart. Spacing groups content without a single border or line.

Contrast · Repetition · Alignment · Proximity — a checklist you can run on any screen.

Design · the words

Typography: most of a UI is text

  • One or two typefaces — more looks chaotic.
  • A type scale — a few defined sizes (e.g. 14 / 16 / 20 / 32), not random ones, to build hierarchy.
  • Line length — ~50–75 characters; long lines are tiring to read.
  • Line height — ~1.4–1.6 for body text, so lines breathe.

Why it matters

Readable type is invisible — people just absorb the content. Bad type (tiny, cramped, low-contrast, ten sizes) makes even simple screens feel hard, and most users won't know why — they'll just leave.

Design · colour

Colour with a purpose

Colour is a tool, not decoration. A small, deliberate palette beats a rainbow:

  • A neutral base (greys/whites) for most of the screen.
  • One accent for the primary action and key highlights.
  • Reserved colours for meaning: success, warning, error.

Contrast is non-negotiable

Text must stand out from its background — aim for a 4.5:1 ratio for body text (WCAG AA). Never use colour alone to signal meaning; ~1 in 12 men can't distinguish red from green.

Design · scaling it

Consistency & design systems

A design system is a reusable kit: defined colours, type, spacing, and components (buttons, inputs, cards) used the same way everywhere.

It makes products feel coherent and teams faster — you assemble screens from trusted pieces instead of reinventing a button each time.

This is exactly React's model

A React component is a reusable UI piece — the same idea as a design-system component, in code. The card you'll build in Lab 8 (QuizCard) is rendered many times, identically. Design thinking and component thinking line up.

Usability · rules of thumb

A few of Nielsen's usability heuristics

Visibility of status

Always show what's happening — loading, saved, failed. Never leave the user guessing.

Match the real world

Use words and concepts people know, not system jargon. Speak the user's language.

User control & freedom

Provide a clear way out: cancel, back, undo. Let people escape mistakes easily.

Error prevention & recovery

Stop errors before they happen; when they do, explain plainly and how to fix them.

Plus: consistency, recognition over recall, and "less is more." Ten in total — these are the load-bearing ones.

Usability · for everyone

Accessibility is part of "done"

Accessibility (a11y) means people with disabilities can use your app — and the same habits make it better for everyone.

  • Enough colour contrast; don't rely on colour alone.
  • Keyboard usable — not everyone uses a mouse.
  • Real labels on inputs and buttons (screen readers read them).
  • Meaningful alt text on images.

The mindset

Curb cuts help wheelchairs and strollers, luggage, bikes. Accessible design is rarely just for a few — captions, clear contrast and big tap targets help everyone, on a bright street or a small phone.

Wrap-up

What to carry into the build

  • The frontend runs in the browser; it's HTML + CSS + JS over the DOM.
  • UX is how it works; UI is how it looks — you need both.
  • Hierarchy, alignment, type and colour make a screen feel intentional.
  • Design every state, stay accessible, keep it consistent.
