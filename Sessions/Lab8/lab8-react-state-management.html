Concepts · the frontend

Where your code runs: the browser

Everything in Labs 5–7 runs on a server: it owns the database, enforces the rules, and answers requests with data (JSON). It has no idea what anything looks like.

The frontend is the other half. It runs in each user's browser, turns that data into pixels, and reacts to clicks and typing. The two halves talk over HTTP — the same fetch you'll write today.

Backend on a server

C# + EF Core + SQL. Owns data, auth, business rules. Speaks JSON.

Frontend in the browser

React + TypeScript. Renders the UI, handles interaction, calls the API.

Concepts · the building materials

HTML, CSS, JavaScript — three jobs

Every web page is made of the same three things, each with one job:

  • HTML — the structure: headings, paragraphs, buttons.
  • CSS — the style: colour, spacing, layout.
  • JavaScript — the behaviour: what happens when you click or type.

React's twist: you write HTML-like markup (JSX) inside JavaScript, so a component keeps its structure and its behaviour together in one file.

<!-- HTML: structure --> <button id="run">Run quiz</button> /* CSS: style */ #run { background: #2563eb; color: white; } // JavaScript: behaviour document.querySelector('#run') .addEventListener('click', startQuiz);
Concepts · why a framework

From hand-editing the DOM to React

The browser parses your HTML into the DOM — a live tree of objects representing the page. Plain JavaScript means you find nodes and change them by hand.

Fine for one button. For a whole app it's a nightmare: the screen and your data drift out of sync, and you're forever patching the DOM to catch up.

What React buys you

You describe what the screen should look like for the current data. Change the data; React updates the DOM to match. You stop touching the DOM at all.

// vanilla: keep poking the DOM by hand let count = 0; btn.addEventListener('click', () => { count++; label.textContent = count; // don't forget this… badge.style.display = count ? 'block' : 'none'; // …or this… }); // React: change data, the UI follows const [count, setCount] = useState(0); // <button onClick={() => setCount(count + 1)}>{count}</button>
Bridging to the backend

Two small changes the API needs first

The browser is a stricter caller than Swagger was. Two changes, already made in Lab8/api, before React can talk to it at all:

  • CORS — the API must explicitly allow the Vite dev server's origin, localhost:5173.
  • Temporarily open GET — signing in from the browser (MSAL) is its own lesson, coming later. For today, reading is public; writing still isn't.

Scope, narrowed on purpose

[Authorize] stays on the controller. POST, PUT and DELETE still need a valid token and will 401 straight from the browser too — only GET gets [AllowAnonymous], and only for this lab.

// Program.cs — let the Vite dev server call us builder.Services.AddCors(o => o.AddDefaultPolicy(p => p.WithOrigins("http://localhost:5173") .AllowAnyHeader().AllowAnyMethod())); // ... app.UseCors(); // before UseAuthorization app.UseAuthentication(); app.UseAuthorization(); // QuizzesController.cs — read stays open, for now [HttpGet] [AllowAnonymous] // ← temporary public async Task<...> GetAll() { ... }
Concepts · the big idea

Declarative UI: describe what, not how

Plain JavaScript pushes you toward telling the browser exactly which DOM node to find and mutate, one step at a time. React asks a different question: given the current data, what should this look like?

A component is a function that answers that question. When the data changes, you don't touch the DOM yourself — you describe the new "what", and React figures out the "how".

// imperative — you do the DOM surgery const el = document.getElementById('count'); el.textContent = count; el.style.color = count > 5 ? 'red' : 'black'; // declarative — describe the result, React does the rest return <span style={{ color: count > 5 ? 'red' : 'black' }}> {count} </span>;
Concepts · building blocks

A component is just a function

It takes inputs, and returns JSX — markup that looks like HTML but is plain JavaScript under the hood. Capitalised name, one piece of UI, reusable wherever you need that piece.

JSX compiles to React.createElement(...) calls — the curly braces { } are your escape hatch back into real JavaScript.

// QuizCard.tsx type QuizCardProps = { title: string; description?: string; }; function QuizCard({ title, description }: QuizCardProps) { return ( <div className="quiz-card"> <h3>{title}</h3> {description && <p>{description}</p>} </div> ); } export default QuizCard;
Concepts · data flow

Props: data flows down, one way

Props ("properties") are how a parent hands data to a child — exactly like function arguments. The child reads them; it never changes them.

The rule

If a component owns the value and can change it — that's state (next slide). If it's handed in from outside and only read — that's a prop.

// App.tsx — the parent passes data down <QuizCard title="C# fundamentals" description="Variables, types, control flow" /> // QuizCard.tsx — the child just receives it function QuizCard({ title, description }: QuizCardProps) { // title, description are read-only here }
Concepts · the missing piece

State: data a component owns — and can change

useState is a hook — a function that plugs a component into React's machinery. It gives you a value, and a setter that schedules a re-render with the new value.

import { useState } from 'react'; function ExistingQuizzes() { const [quizzes, setQuizzes] = useState<ApiQuiz[]>([]); // ^value ^setter ^initial value // calling setQuizzes(...) re-renders this component // with the new array — you never push() into quizzes directly }

Props

Passed in from a parent. Read-only. Change → parent re-renders the child.

State

Owned by this component. Mutable via its setter. Change → this component re-renders.

What "re-render" actually means

You never call the function yourself, and you never touch the DOM. You just change the data; React decides what needs to move.

Concepts · reaching outside React

useEffect: for everything that isn't rendering

Fetching data, timers, subscriptions — "side effects" that happen because the component rendered, not part of describing the UI itself. useEffect runs after render, and again whenever its dependencies change.

import { useEffect, useState } from 'react'; function ExistingQuizzes() { const [quizzes, setQuizzes] = useState<ApiQuiz[]>([]); useEffect(() => { fetchQuizzes().then(setQuizzes); }, []); // ← empty array: run once, on mount return /* ... */; }

The classic gotcha

Drop the [] and the effect runs after every render — which, if it calls setQuizzes, triggers another render, which runs the effect again. An infinite fetch loop, and it's the #1 thing people get wrong in their first week of React.

Concepts · meeting the backend

Connecting to the real API

Plain fetch today — no library yet. The ApiQuiz type below mirrors the C# model from Lab 6 field for field, so the shape shouldn't be a surprise.

Because of the [AllowAnonymous] change from slide 5, no Authorization header is needed for this call — a deliberate simplification, not a permanent one.

type ApiQuiz = { id: string; title: string; description?: string; ownerId: string; }; async function fetchQuizzes(): Promise<ApiQuiz[]> { const res = await fetch('http://localhost:5023/quizzes'); if (!res.ok) throw new Error(`HTTP ${res.status}`); return res.json(); }

Concepts · where state lives

Lifting state up

State lives in the closest component that needs it — or, if several components need the same data, in their nearest common ancestor. The built quizzes live in App because the builder adds to them and the home list and runner read from them.

But notice what doesn't get lifted: the half-finished questions inside QuizBuilder stay local — no one else needs them, so lifting them would just be noise.

Today vs. next session

Today: state lifted one level into App, plus local state inside the builder and runner. Props down, callbacks up.

Next session brings the Context API — for state that genuinely needs to be shared across a whole screen, when passing props down many levels stops scaling.

Watch out

Things people get wrong on day one

  • Missing dependency array — useEffect(fn) with no [] runs every render; combined with a state-setting fetch, that's an infinite loop.
  • No key prop on a list — mapping quizzes to <QuizCard> without a stable key={quiz.id} causes React warnings and reordering bugs.
  • Mutating state directly — quizzes.push(x) changes the array but doesn't tell React. Always go through the setter: setQuizzes([...quizzes, x]).
  • CORS errors in the console — means UseCors() is missing, in the wrong order, or the origin doesn't match localhost:5173 exactly.
  • Forgetting only GET is open — POST/PUT/DELETE still need a Bearer token; calling them from the browser today will 401, same as Lab 7.
  • Confusing props and state — if it's passed in, it's a prop; if this component owns and changes it, it's state.
Wrap-up

What you can do now

You took a backend-only API and gave it its first screen — then went past read-only into the real work of state management.

  • Build functional components driven by props
  • Use useEffect to fetch on mount, with loading & error states
  • Hold nested data (quiz → questions → answers) in useState and update it immutably
  • Lift state to the right level and switch screens from it

Where this goes next

Real forms and validation, and the Context API where prop-drilling stops scaling. A component library for real styling. And eventually, wiring sign-in (MSAL) into the browser so "Create quiz" can actually POST — closing the gap this lab deliberately left open.
