AI-generated quizzes & real grading

QuizMaster can already fetch from the API, and build and run a quiz in the browser. Today it grows up in three directions at once: you'll sign in for real with your Microsoft account instead of pasting a token from Swagger, the backend can write a quiz for you from a block of pasted text, and the server — not the browser — now decides what's correct. By the end you'll sign in once, paste a paragraph, watch a quiz appear, take it, and get a real score.

Part B · Sign in for real, with MSAL
02

Sign in for real, with MSAL

Every lab since 7 has had the same awkward step: open Swagger, click Authorize, sign in there, copy the token it hands you, paste it into a plain <input type="password"> in the React app. It worked, but it was never the real thing — a production app doesn't ask its users to visit a different website and copy-paste a string to prove who they are. Today that goes away. QuizBuilder keeps its "Access token" field for one more step; by the end of this one, it's gone for good, replaced by an actual Sign in with Microsoft button.

The library doing the work is MSAL — the Microsoft Authentication Library. @azure/msal-browser handles the actual OAuth2/OIDC dance with Microsoft's identity platform (popups, redirects, token caching, silent renewal); @azure/msal-react is a thin wrapper that exposes all of that as hooks (useMsal, useIsAuthenticated) so components can read sign-in state the same way they read any other piece of React state. Both are already in package.json — npm install in step 00 already pulled them in.

The pieces, before you write any code:

  • One app registration, two roles. The backend has trusted an Entra ID app registration since Lab 7 (Lab9/api/appsettings.json's AzureAd section — Client ID 5c2ab77a-5cfb-4b0e-aa3c-327f600296e6, tenant consumers). The API validates tokens against that registration; today, the React app signs users in and asks Microsoft for a token under that same registration. One registration, one Client ID, two different roles.
  • A second redirect URI. That app registration's "Single-page application" platform currently only lists Swagger's redirect URI (http://localhost:5023/swagger/oauth2-redirect.html). MSAL in the React app runs on Vite's dev server instead — http://localhost:5173 — so it needs to be added as a second redirect URI on the same platform entry. Your instructor should have already done this; if sign-in fails with AADSTS50011 ("redirect URI ... does not match"), that's the first thing to check.
  • src/auth/authConfig.ts is already there, given upfront the same way types/quiz.ts was in Lab 8 — there's no lesson in typing out a Client ID by hand. Open it and read it: it exports msalConfig (the PublicClientApplication's settings — Client ID, authority, redirect URI, where to cache tokens) and loginRequest (the one scope this app ever asks for, the API's own access_as_user).

Why a popup, not a redirect? MSAL supports both loginRedirect (navigates the whole page away to Microsoft and back) and loginPopup (opens a second window, the main app never unmounts). For a small app like this one, a popup keeps your component state intact across sign-in — no need to persist quizzes or view through a full-page navigation. Production SPAs use both patterns; popups are the easier one to reason about for a lab.
Why acquireTokenSilent, not just store the token? Access tokens expire — usually within an hour. A token you stored at sign-in time would quietly start failing later in the session with a 401, for a reason that has nothing to do with anything you did. acquireTokenSilent re-checks (and silently renews) on every call, so the token you send is always the freshest one MSAL has, no matter how long you've had the tab open.
02b

Promote sign-in to its own page (the gate)

Right now sign-in is a button in the corner, and the whole app is usable signed out — you can browse quizzes, open the builder, and only get stopped at the moment you try to save. That's fine for a demo, but most real apps put a front door first: a dedicated sign-in page that the rest of the app lives behind. Let's do that — a hard gate. Until you're signed in, the only thing you can see is the sign-in page; once you are, the app appears in its place.

The nice part: we already have everything we need. useIsAuthenticated() from step 02 is the only signal the gate needs — no new library, no router.

First, a tiny presentational component for the page. It owns one job: start a sign-in and show "opening…/error". It never touches a token.

Sign-in popup blank, or "redirect_uri is not valid"? If the popup opens blank / stuck on about:blank, give it a second — it usually resolves to a Microsoft error: "The provided value for the input parameter redirect_uri is not valid" (a.k.a. AADSTS50011). That's not a bug in your code: it means http://localhost:5173 hasn't been registered as a redirect URI on the app registration, under the Single-page application platform (not "Web"). Your instructor adds this once for the whole cohort — flag it to them if you hit it. Also confirm the app is actually served on http://localhost:5173 (if Vite reports a different port because 5173 was taken, the registered URI won't match).
Separation of concerns — why three pieces, not one. AuthPage knows how to start a sign-in. App decides whether to show the app or the door, from one boolean. getAccessToken knows how to get a token when a write needs one. None of them reaches into the others' job. That's why this whole gate is a four-line change instead of a rewrite: each piece has one reason to change, and you can swap one (popup → redirect, gate → real router) without touching the rest. A component that fetched data, decided routing, and managed tokens would be three concerns tangled together — hard to test, harder to change.
"Navigation" without a router. We never call history.push or define a route. The gate is just conditional rendering driven by state — the same pattern as the view switch inside App. When an app grows past a handful of screens (real URLs, the back button, deep links), that's when you reach for a router like React Router. Until then, a boolean and an early return is the simpler tool, and it's worth seeing that "going to a page" is, underneath, just rendering different JSX.

Mark a correct answer in QuizBuilder

Open src/components/QuizBuilder.tsx. Two changes.

First, give every new answer a default. In addAnswer:

src/components/QuizBuilder.tsx
function addAnswer(qid: string) { setQuestions((qs) => qs.map((q) => q.id === qid - ? { ...q, answers: [...q.answers, { id: newId(), text: '' }] } + ? { ...q, answers: [...q.answers, { id: newId(), text: '', isCorrect: false }] } : q, ), ); }

That alone fixes the build. But right now there's no way to ever set isCorrect to true — you need a way to mark one answer per question as correct, radio-button style (picking a new one unpicks the old one, in the same question only).

Second, add a markCorrect function:

function markCorrect(qid: string, aid: string) { setQuestions((qs) => qs.map((q) => q.id === qid ? { ...q, answers: q.answers.map((a) => ({ ...a, isCorrect: a.id === aid })) } : q, ), ); }

Read that map closely: every answer in the matching question gets a new object where isCorrect is a.id === aid — true for the one you clicked, false for every other one in that question. One line, no separate "clear the old one first" step, because you're not mutating anything — you're computing the whole next state in one pass. Answers in other questions are untouched (the outer q.id === qid check skips them entirely).

Now wire it into the JSX. Inside the q.answers.map(...) block, add a radio input before each answer's text input:

<div className="answer-row" key={a.id}> <label className="answer-correct-toggle" title="Mark as the correct answer"> <input type="radio" name={`correct-${q.id}`} checked={a.isCorrect} onChange={() => markCorrect(q.id, a.id)} /> </label> <input type="text" value={a.text} placeholder="Answer option" onChange={(e) => updateAnswerText(q.id, a.id, e.target.value)} /> <button className="btn-ghost" onClick={() => removeAnswer(q.id, a.id)}> ✕ </button> </div>
Why the name and the checked prop matter name={`correct-${q.id}`} is what makes the radios behave like a group per question — without it, every radio on the whole page would compete with every other one. checked={a.isCorrect} makes the input a controlled component: React, not the browser, decides which radio looks selected, because it's reading straight off your state.

export async function generateQuiz( token: string, input: { sourceText: string; title?: string; questionCount?: number }, ): Promise<ApiQuiz> { const res = await fetch(`${API_BASE}/quizzes/generate`, { method: 'POST', headers: authHeaders(token), body: JSON.stringify(input), }); if (!res.ok) { if (res.status === 502) throw new Error('Quiz generation failed — check the API logs / GITHUB_TOKEN.'); throw new Error(`Generate quiz failed: HTTP ${res.status}`); } return res.json(); }

The 502 special-case matters: a 502 here means the model's response misbehaved (a bad token, the model returning something the backend couldn't parse into a quiz), which is a different failure than a normal bad request — worth a clearer message than "HTTP 502" for your future self.

Build PlayQuiz, part 2: submit & show the grade

Add evaluateQuiz to src/api/quizzes.ts, alongside fetchPlayQuiz:

export async function evaluateQuiz( quizId: string, answers: { questionId: string; selectedOptionId: string | null }[], ): Promise<QuizResult> { const res = await fetch(`${API_BASE}/quizzes/${quizId}/evaluate`, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ answers }), }); if (!res.ok) throw new Error(`Evaluate failed: HTTP ${res.status}`); return res.json(); }

Again no Authorization header — grading is [AllowAnonymous] too, on purpose: it's a read/compute over data the server already has, not a write. Add QuizResult to the type import at the top of quizzes.ts.

Back in PlayQuiz.tsx, add the result state and a submit function:

const [result, setResult] = useState<QuizResult | null>(null); const [submitting, setSubmitting] = useState(false); async function submit() { if (!quiz) return; setSubmitting(true); setError(null); try { const answers = quiz.questions.map((q) => ({ questionId: q.id, selectedOptionId: picks[q.id] ?? null, })); const graded = await evaluateQuiz(quiz.id, answers); setResult(graded); } catch (err) { setError((err as Error).message); } finally { setSubmitting(false); } }

Notice picks[q.id] ?? null — a question the student never clicked an answer for still gets sent, as null, rather than silently dropped. The server can then correctly mark it wrong (or, for a text-only question, ignore it) instead of you having to special-case "missing" on the client.

That's the whole design: the server graded the submission and is now telling the browser what was right, after the fact. The browser was never in a position to cheat, because it never held the answer key.
