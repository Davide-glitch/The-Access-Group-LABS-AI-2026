Part 1 of 3

Concepts

The ideas behind today, before we touch a line of React. Everything in this part is the why — the security reasoning and the design vocabulary the rest of the lab leans on.

Recap

Where Lab 8 left off

QuizMaster could fetch quizzes from the API, and build and run a quiz entirely in the browser: a title, some questions, some answer options, all living in React state.

Three honest limitations

  • Signing in meant pasting a bearer token copied out of Swagger.
  • Writing every question by hand doesn't scale past a handful of quizzes.
  • "Running" a quiz with no concept of correctness isn't really a quiz.

All three addressed today.

Gap one

A pasted token isn't sign-in

Copy-pasting a bearer token out of Swagger was always a teaching shortcut, not a real auth flow. It only worked because you had Swagger open next to the app. A real user never sees a token, never opens a developer tool, and shouldn't have to — they expect a button that says Sign in.

What changes first today

A real Microsoft sign-in popup, via MSAL, replaces every place the app used to ask for a pasted token.

Gap two

Writing quizzes by hand doesn't scale

Imagine you're a teacher with a 2,000-word reading on photosynthesis and you want a 6-question check for understanding. Typing that by hand is mechanical work: reread the text, extract facts, phrase a question, write three plausible wrong answers, repeat six times.

Tedious for a human, tractable for a model

The source material is right there, and the output shape (question + options + one correct answer) is rigid and checkable — exactly the kind of task a language model is good at, and exactly the opening today's lab walks through.

Real auth

MSAL replaces the paste

const { instance, accounts } = useMsal(); async function getAccessToken() { const account = accounts[0]; try { const result = await instance.acquireTokenSilent({ ...loginRequest, account }); return result.accessToken; } catch { const result = await instance.acquireTokenPopup(loginRequest); return result.accessToken; } }

acquireTokenSilent first — reuse a cached token with no UI at all — and only fall back to a popup if that fails (first sign-in, expired session).

No more pasted state

Every fetch that used to read a pasted token from React state now calls getAccessToken() instead. No component below App ever stores or passes a raw token string by hand anymore.

Setup

Same app registration, one more redirect URI

No new Entra app registration this week — the React app signs in against the same app registration the API has trusted since Lab 7.

One shared identity, two front doors

The only setup change is a second redirect URI on that registration's Single-page-application platform (http://localhost:5173, alongside Swagger's existing one), so the browser's sign-in popup has somewhere to land. Swagger for testing, the React app for real use.

The fix

Send the text, get a quiz back

POST /quizzes/generate takes a longer piece of pasted text and a questionCount, and returns a brand-new quiz — persisted exactly like one a student built by hand: same database table, same AddQuestionAsync, same validation rules.

Under the hood it's nothing more exotic than a chat request with instructions and a JSON shape to fill in. One instruction string, one JSON schema, one call — no multi-step planning, no memory between calls, no tools.

var messages = new List<ChatMessage> { new SystemChatMessage("Turn source text into a quiz. " + "Every question needs exactly four options, exactly one isCorrect."), new UserChatMessage(prompt), }; var completion = await chatClient.CompleteChatAsync(messages, new ChatCompletionOptions { ResponseFormat = ChatResponseFormat.CreateJsonSchemaFormat("quiz", quizSchema) });
Concepts · the catch

Validate everything that comes back

foreach (var q in payload.Questions) { if (q.Options.Count < 2 || q.Options.Count(o => o.IsCorrect) != 1) throw new InvalidOperationException( $"The model returned a malformed question (\"{q.Text}\"): " + "needs 2+ options and exactly one marked correct."); }

Asking for JSON in a fixed shape is a strong nudge, not a guarantee — a model can still return a question with one option, or two marked correct. So the response gets checked before anything is saved, exactly like any other input you don't control.

A bad response becomes a 502 to the caller, not a broken quiz silently saved to the database.

Asking nicely for a shape doesn't remove the need to check it landed.

The core idea

The security lesson

Here's the question this whole lab is really about: once a quiz has a correct answer, where is it safe to say so out loud?

In the database

Fine — that's the source of truth.

To the quiz's owner

Fine — they're allowed to know what they wrote.

To a student about to take it

Not fine. Open the network tab and there it is, before they've answered a single question.

A client-submitted "I got this right" flag is exactly as trustworthy as asking a student to grade their own exam and just believing them. The fix is never sending the answer key to a client that hasn't earned it yet.

Three views, one trust boundary

Three views of the same Quiz

DTOUsed byHas IsCorrect?
Quiz (full entity) the owner's "On the server" list yes
PlayQuizDto a student about to answer no
QuizResultDto a student who already submitted yes — now it's safe

A view model is a trust boundary, not just a data-shaping convenience.

Mechanics

Why grading happens on the server, not the client

PlayQuiz never has the correct answers, so it cannot grade locally — and that's not a missing feature, that's the design working as intended.

The client's only job is to remember which option the student clicked and ship that to POST /quizzes/{id}/evaluate. The server looks up the real Question.Options, finds the one where IsCorrect, and compares.

One source of truth

The grading logic exists in exactly one place (QuizzesController.Evaluate), not duplicated between a "preview" client calculation and a server-side double-check.

Concepts · the why

Separation of concerns

Keep this in mind as we head into the frontend next: each piece of the sign-in flow we're about to build has one job, and deliberately doesn't know about the others. That's what makes the gate a four-line change instead of a rewrite.

AuthPage

Knows how to start a sign-in and show "opening…/error". It owns no token and decides nothing about routing.

App (the gate)

Decides whether to show the app or the door, from one boolean. It doesn't know how a popup works.

getAccessToken / authConfig

Knows how to get a token when a write needs one. Nobody else touches MSAL's token APIs.

Same instinct as the backend's DTOs: a clear boundary, each side responsible for one thing, so a change on one side doesn't ripple across the other.

Concepts · the payoff

Why we bother drawing the line

Each piece is testable alone

You can render AuthPage with a fake MSAL instance and never spin up the whole app. The gate is just "boolean in, which screen out".

Swap one without touching the rest

Move from a popup to a redirect flow, or replace the gate with a real router later — AuthPage and the token logic don't change. The seam is where you want it.

A component that fetches, decides routing, and manages tokens is three concerns in a trench coat — hard to test, harder to change.

Frontend · zooming out

The other hook calls in play

A "hook" is just a function starting with use that lets a component tap into React (or a library's) state and lifecycle. You've now met a handful — worth naming them side by side.

HookWhere it shows upWhat it gives you
useState AuthPage, QuizGenerator, PlayQuiz local state that survives re-renders (signing-in flag, answers map)
useEffect PlayQuiz, ExistingQuizzes run a side effect (the fetch) on mount / when a dep changes
useMsal App, AuthPage the MSAL instance + accounts from the provider
useIsAuthenticated App (the gate) a one-line "is anyone signed in?" boolean

useMsal and useIsAuthenticated are library hooks — same rules as React's own, they just read from the MsalProvider that main.tsx wraps the app in.

Frontend · for later

Hooks you haven't needed — yet

useContext

Read shared data without passing props down every level. It's how useMsal reaches the provider behind the scenes.

useMemo / useCallback

Cache an expensive result, or a stable function reference, so it's not rebuilt on every render. Reach for these only when you measure a real cost.

useRef

Hold a value (or a DOM node) across renders without triggering one — e.g. focusing the sign-in button on mount.

And: your own

Anything that calls other hooks can become a custom hook — e.g. useQuiz(id) wrapping the fetch-on-mount in PlayQuiz. Same rules: call hooks at the top level, only from components or other hooks.

Part 2 of 3

Frontend

Now the React you actually write — the sign-in page and gate, the token plumbing for writes, and the three screens that turn the concepts above into something you can click.

Frontend · new this lab

A dedicated sign-in page, as a gate

Rather than tucking sign-in into the corner of a browsable app, App renders a full-screen AuthPage until someone is signed in. There's no "browse as a guest" path — the front door comes first.

The whole gate is one early return, driven by the same useIsAuthenticated() boolean the header already used.

const isAuthenticated = useIsAuthenticated(); // Until MSAL reports an account, the whole // app is replaced by the sign-in screen. if (!isAuthenticated) { return <AuthPage />; } // Past this line, the user is always // signed in — the rest of App can assume it. return <div className="app"> /* … */ </div>;

"Navigate to the main page" with no router

When the popup succeeds, useIsAuthenticated() flips, App re-renders, the early return stops firing, and the app appears in AuthPage's place. The "navigation" is just React rendering a different branch — no history.push, no route table.

Frontend

Signing in for real

A Sign in with Microsoft button, wired to instance.loginPopup().

Every write, backed by a real token

Once signed in, getAccessToken() backs every write — Create, AddQuestion, Generate — with a real token, and the header reads "Signed in as ...". No component below App stores or passes a token string by hand anymore; they ask for one when they need it.

Frontend

QuizGenerator — a familiar shape, a new trigger

QuizGenerator has no "build it yourself" state at all — no nested question arrays, no immutable updates.

The same fetch lifecycle, different trigger

It has exactly the same three states as ExistingQuizzes's data fetch — idle → in flight → done or error — just triggered by a click instead of mount, and a POST instead of a GET. If you've internalized the fetch lifecycle from Lab 8, you already know this component; only the trigger — and the text box it sends — changed.

Frontend

PlayQuiz — answer, then submit, then reveal

Three phases, one component:

  1. Fetch the play shape on mount (useEffect, keyed on quizId this time — a different quiz id should mean a fresh fetch).
  2. Answer, one question at a time, recorded in a questionId → optionId map — nothing sent anywhere yet.
  3. Submit the whole map at once, and let result (once it exists) take over the render entirely — the graded view and the answering view are mutually exclusive, driven by one piece of state.
Frontend

Putting it together: one play view in App

Lab 8 had run (a local quiz) and run-server (a quiz fetched from the API) as two separate views feeding two different shapes into QuizRunner.

Today: one view

They collapse into one play view, because by the time QuizBuilder.save() returns, a "local" quiz and a "server" quiz are the exact same row in the database. PlayQuiz only ever needs an id — it goes and fetches the no-peeking shape itself, regardless of whether that quiz was typed by hand or generated from pasted text five seconds ago.

Part 3 of 3

Backend & wrap-up

The endpoints that make it all real, how the server withholds the answer key, and the things people trip over on day one.

At a glance

New backend endpoints

EndpointAuthJob
POST /quizzes/generate required source text in → model drafts the quiz → checked → saved, same as a hand-built one
GET /quizzes/{id}/play public the no-peeking shape — questions and options, no isCorrect
POST /quizzes/{id}/evaluate public submitted picks in → server grades → result with isCorrect revealed

Generating is a write (it creates rows), so it's [Authorize]d like POST /quizzes always has been — the same sign-in from earlier in this deck is what makes that header real now, not pasted. Playing and evaluating are reads/computes over data the server already owns — public, even though one of them is a POST.

Mechanics

Why GET /play strips isCorrect

Options = q.Options.Select(o => new PlayOptionDto { Id = o.Id, Text = o.Text }).ToList()

PlayOptionDto simply doesn't have an IsCorrect property — there's no flag being set to false or hidden in the frontend, because that would still mean the correct answer made it into the HTTP response somewhere, and anyone can open dev tools.

Structural, not behavioral

The guarantee comes from the type itself — it cannot carry the answer, because the field doesn't exist on it.

Mechanics

Defense in depth: client mirrors server

if (q.answers.filter((a) => a.isCorrect).length !== 1) { setWarning(`Mark exactly one correct answer for "${q.text}".`); return; }

The server rejects a question with one option, or with zero-or-two-plus correct answers. So does QuizBuilder.save(), before the request is even sent.

Not redundant

The server check is the one that actually matters for security — never trust a request just because it came from "your own" frontend. The client check exists purely for experience: a specific, friendly message instead of a generic failed request.

Watch out

Things people get wrong on day one

  • Sign-in popup blocked or AADSTS50011 — a browser popup blocker, or the redirect URI from earlier in this deck hasn't been added to the app registration yet.
  • Forgetting GITHUB_TOKEN before starting the API — the server still boots fine; only the first /generate call fails, which can look like a routing bug if you don't know to check for it.
  • Treating a 502 like any other failed request — it means the model's response didn't pass validation, not that the request itself was malformed.
  • Putting isCorrect checks in the frontend and assuming that's "secure" — it's a UX nicety; the server check is the only one an attacker can't skip.
  • Forgetting the per-question radio name — without name={`correct-${q.id}`}, marking one question's answer correct un-marks every other question's answer too.
Wrap-up

What you can do now

  • Explain, in one sentence, why a pasted bearer token isn't the same thing as signing in.
  • Explain, in one sentence, why PlayQuizDto has no IsCorrect field.
  • Trace a generated quiz from a pasted paragraph all the way to a graded result, naming every endpoint it touches along the way.
  • Build a new endpoint that returns a different view of an existing entity, deliberately omitting a field a particular caller shouldn't see.
  • Ask a model for a JSON-shaped response, and explain why you'd still validate it after deserialization succeeds.
